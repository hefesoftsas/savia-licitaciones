# API web de Savia (desarrollo local)

Este módulo contiene la API inicial de la aplicación web y el runner; el recorrido web está en desarrollo y no está listo para producción. Su configuración D1 es exclusivamente local: no se han creado recursos en Cloudflare.

Desde la raíz, instala las dependencias siguiendo `DEPENDENCY_POLICY.md` y utiliza el sitio local de un solo origen descrito a continuación. Para ejecutar las pruebas de la API aislada, usa `pnpm run test:web-api` desde la raíz; estas compilan el Worker y utilizan Miniflare y D1 temporales. No reutilices los secretos de prueba en ningún otro entorno.

Por defecto, la cuenta local utiliza correo y contraseña sin verificación de correo. El alta y la recuperación admiten correo cuando se configura el binding; antes de permitir usuarios reales hay que configurar y verificar la entrega y exigir la verificación.

Para crear la primera cuenta de administración, configura `SAVIA_SUPERADMIN_EMAIL` y `SAVIA_SUPERADMIN_PASSWORD` como secretos del entorno; `SAVIA_SUPERADMIN_NAME` es opcional. Después de aplicar las migraciones, la primera petición a la API crea una sola cuenta con el rol `superadmin` de Better Auth. La contraseña se guarda mediante el algoritmo de Better Auth y no se almacena en el repositorio. La creación no convierte una cuenta existente: si el correo ya está registrado, la API informa un error de configuración y hay que elegir otro correo. Una vez creada la cuenta, cambiar o eliminar esas variables no modifica el usuario ni restablece su contraseña; usa los flujos de administración o recuperación de Better Auth para esos cambios. El rol habilita los controles de administración de identidad de Better Auth; en Cuenta permite consultar usuarios, suspender o restablecer su acceso y cambiar sus roles. Suspender una cuenta cierra sus sesiones. Los datos de proyectos siguen sujetos al aislamiento por propietario.

Better Auth usa D1 para compartir los contadores de límite de autenticación entre instancias; se necesitan las migraciones `0133` y `0134`. La IP se toma de `cf-connecting-ip`, por lo que el servicio debe recibir tráfico mediante Cloudflare. Si no llega una IP confiable, Better Auth usa un contador compartido por ruta. El inicio de sesión por correo admite cinco solicitudes por diez segundos por IP, y el cambio de contraseña diez por diez segundos; las demás rutas mantienen las reglas de Better Auth. La tabla guarda una huella HMAC de la IP y la ruta, el contador y la fecha del último intento; no guarda IP, ruta ni contraseñas en claro. El secreto de autenticación se usa para calcular la huella; cambiarlo también reinicia los contadores efectivos. La limpieza de registros con más de 24 horas es oportunista y no garantiza un plazo máximo de conservación: debe definirse y verificarse una política antes de producción. La migración `0134` retira contadores anteriores guardados en texto claro; todas las instancias deben actualizarse para que no vuelvan a crearlos. Véase la [documentación de límites de Better Auth](https://better-auth.com/docs/concepts/rate-limit).

## Sitio compilado en un solo origen local

Esta modalidad sirve la interfaz y la API desde `http://127.0.0.1:8788` con Wrangler y Miniflare. Desde la raíz ejecuta `pnpm run build:web`; después, en `web-api/.dev.vars`, configura `BETTER_AUTH_URL=http://127.0.0.1:8788`, un `BETTER_AUTH_SECRET` aleatorio de al menos 32 caracteres y las variables de cifrado descritas abajo. Desde `web-api/` ejecuta `pnpm run migrate:site` y `pnpm run dev:site`.

La configuración local incluye un binding de correo simulado. Para probar la verificación obligatoria agrega `AUTH_REQUIRE_VERIFIED_EMAIL=true` a `.dev.vars`; el enlace aparece en la salida local de Wrangler, que debe tratarse como información confidencial. El remitente local `savia@example.com` es de prueba. Para una instalación real hay que habilitar un dominio remitente en Cloudflare Email Service, configurar el binding `EMAIL` y `AUTH_EMAIL_FROM`, y verificar la entrega antes de activar el requisito. No se envía correo real con el binding local.

`pnpm run test:web-assets`, desde la raíz, compila la interfaz y verifica registro, sesión, proyectos, emparejamiento y una tarea con Pi y el adaptador OpenCode Go en un origen local temporal. La respuesta del proveedor se simula y la prueba bloquea destinos externos inesperados; no verifica una cuenta o servicio real. La configuración `wrangler.web.local.jsonc` utiliza identificadores locales, no configura recursos remotos y no está preparada para desplegar. El enrutamiento SPA devuelve la página principal para rutas estáticas desconocidas; las rutas `/api` se procesan en el Worker, incluso durante la navegación.

La misma prueba ejecuta otra tarea desde un proceso independiente del CLI. Para comprobar una distribución ya construida en el sistema de destino, establece `SAVIA_TEST_RUNNER_CLI` a la ruta absoluta de su `runner/cli.mjs` y ejecuta `node --test web-api/test-assets/site.test.mjs` desde la raíz, después de compilar la web. El recorrido se ha comprobado con la distribución de macOS ARM64; no sustituye una prueba interactiva del navegador ni verifica un proveedor o Cloudflare remoto.

## Plantilla para Cloudflare

La configuración OpenTofu en `infra/web/` prepara la base D1, el bucket R2 y, opcionalmente, el dominio web. La plantilla `wrangler.web.template.jsonc` describe los bindings del Worker, incluido el correo y el Durable Object `PREVIEW_WAKE` con la migración `preview-wake-v1`; contiene identificadores de ejemplo y no crea recursos por sí sola. El código y las migraciones de Durable Objects se publican con Wrangler; las migraciones SQL de D1 se aplican por separado y deben incluir las migraciones más recientes. Ningún runner en la nube se activa con esta configuración. Consulta [infra/web/README.md](../infra/web/README.md) para preparar el plan y el despliegue.

`wrangler.web.template.jsonc` es una plantilla de preparación, no una configuración de producción lista para usar. Contiene valores ficticios para el nombre del Worker, la URL, el remitente, el identificador de clave, la base D1 y el bucket R2. No tiene ruta pública, mantiene `workers_dev: false` y no define recursos de ejecución alojada. La aplicación y la API usan un solo origen: los assets se sirven desde `dist` y las rutas `/api` pasan primero por el Worker.

Para validar la plantilla sin crear recursos ni publicar, ejecuta desde la raíz `pnpm run build:web` y `node --test web-api/test-assets/cloudflare-template.test.mjs`. La prueba usa `wrangler deploy --dry-run`; no aplica migraciones remotas. Las claves `BETTER_AUTH_SECRET`, `CREDENTIAL_KEY_HEX` y, cuando corresponda, `CREDENTIAL_PREVIOUS_KEYS_JSON` deben configurarse como secretos del Worker y no escribirse en la plantilla. Guarda las claves necesarias para restaurar respaldos y sigue el procedimiento de rotación indicado abajo.

Antes de usar una configuración propia habría que sustituir los valores de ejemplo por recursos existentes, definir el dominio y la ruta reales, aplicar las migraciones apropiadas y verificar aislamiento, recuperación, límites y costos. El origen configurado en `BETTER_AUTH_URL` debe coincidir con el sitio. La verificación de correo está activada en la plantilla: el remitente debe pertenecer a un dominio habilitado en Cloudflare Email Service y debe comprobarse que la cuenta puede entregar mensajes a los destinatarios previstos. La documentación de Cloudflare describe las restricciones de los [bindings de envío](https://developers.cloudflare.com/email-service/configuration/send-bindings/). La entrega real, la configuración remota y la preparación para producción aún no se han verificado.

## Eliminación de proyectos

La interfaz permite eliminar un proyecto tras confirmación. La API rechaza la eliminación mientras haya tareas en cola o en ejecución. Registra las claves de archivos y resultados en una transacción antes de borrar el proyecto; después limpia R2 por lotes sin eliminar objetos aún compartidos. Si la limpieza no termina, la interfaz muestra el proyecto retirado y permite reintentarla tras recargar. Los recibos de eliminación se conservan para que el reintento sea idempotente. Requiere aplicar la migración local `0132`; no se ha desplegado ni validado en Cloudflare real.

Las migraciones locales `0136` a `0139` preparan el seguimiento posterior a la presentación: la web permite registrar solicitudes y resultados manuales por proyecto, con una tarea opcional, versiones para el estado de cada solicitud y reintentos idempotentes. Las solicitudes abiertas con fecha aparecen en la agenda y los recordatorios como fechas personales. La interfaz permite adjuntar y descargar archivos de solicitudes; la API verifica su longitud y hash y limpia las cargas fallidas. También permite registrar fecha, radicado y versión con copias verificadas de dos documentos del proyecto como paquete y comprobante. El límite combinado es 256 MiB. Las cargas al proyecto están sujetas a los límites del plan de Cloudflare. Estos datos aún no están incluidos en capturas y restauraciones. No modifica información oficial de SECOP.

## API local inicial

La web incluye un asistente de oferta que presenta las etapas de búsqueda, preparación y revisión, y enlaza a SECOP y a los proyectos. Si hay un proyecto seleccionado, ofrece retomarlo; no crea ni modifica datos por abrir el asistente. Las operaciones siguen realizándose en las pantallas existentes.

El idioma, el modo de color, el color de acento y el estilo web se guardan por cuenta con `GET/PUT /api/preferences`: los valores iniciales son español, sistema, neutro y Vega. El modo de sistema sigue la apariencia del dispositivo. La selección de idioma previa al inicio de sesión es temporal; al entrar se cargan las preferencias de la cuenta. La escritura requiere el mismo origen y cada preferencia se puede actualizar por separado. No se guardan en el navegador ni alteran el formato de los documentos.

La sesión de Better Auth autentica `POST /api/projects`, `GET /api/projects` y `GET /api/projects/:id`. Los documentos se cargan con `POST /api/projects/:id/files`, cuerpo binario y cabecera `X-File-Name` codificada con `encodeURIComponent`. Sus metadatos se consultan con `GET /api/projects/:id/files` y sus bytes con `GET /api/projects/:id/files/:fileId`. El servidor verifica propiedad por sesión; los métodos mutadores requieren `Origin` igual a `BETTER_AUTH_URL`. Los documentos se sirven como descarga.

Esta API inicial no sustituye todavía los stores ni flujos del cliente de escritorio. Las cargas se leen completas en memoria y requieren una estrategia de carga para archivos grandes antes de producción. La persistencia y aislamiento se han probado en Miniflare, no en una cuenta remota.

## Emparejamiento de runner

`POST /api/runner-pairings` crea un código efímero para la sesión; `POST /api/runners/pair` lo canjea una vez por una credencial. `GET /api/runners` lista solo los runners del usuario y `DELETE /api/runners/:id` los revoca. Un runner verifica su conexión con `POST /api/runners/heartbeat` y su credencial Bearer. La respuesta de emparejamiento y el listado incluyen `executionMode: 'local'`; el valor `hosted` está reservado y las identidades marcadas así no pueden autenticarse ni reclamar tareas. Las instalaciones anteriores se migran a `local`. D1 conserva hashes de códigos y credenciales, no los valores entregados. Ver `runner/README.md` para la utilidad local inicial.

## Cola inicial de trabajos

La sesión crea un trabajo con `POST /api/projects/:id/jobs`, JSON `{kind,payload}` y `Idempotency-Key` por solicitud. La misma clave y datos devuelven el trabajo existente; si cambian los datos se rechaza el reintento. `GET /api/projects/:id/jobs` lista los trabajos del propietario y `POST /api/projects/:id/jobs/:jobId/cancel` los cancela.

El runner autenticado reclama únicamente los tipos que anuncia mediante `POST /api/runner/jobs/claim`; renueva una concesión vigente con `POST /api/runner/jobs/:id/renew` y entrega el resultado con `POST /api/runner/jobs/:id/complete`. Las concesiones caducadas quedan `interrupted`, sin repetición automática. Las consultas de documentos, la generación de capítulos técnicos, los análisis de RUP, biblioteca y recomendaciones, y los análisis, índices, parámetros y capítulos de viabilidad informan su etapa mediante códigos limitados durante la renovación. La web recupera la última etapa mientras la tarea está activa, sin registrar contenido como progreso; las tareas breves pueden terminar antes de la primera renovación. El runner intenta guardar y reenviar los resultados pendientes mediante una bandeja local cifrada. Si la concesión ya venció o fue cancelada, conserva la copia para recuperación manual y no reejecuta el trabajo automáticamente. La entrega no está garantizada si falla el almacenamiento local; consulta los detalles y límites en `runner/README.md`.

## Credenciales de proveedor

`POST /api/provider-credentials` guarda `{provider, model, secret}` cifrado con AES-256-GCM; admite límites opcionales de contexto y salida. `GET /api/provider-credentials` devuelve solo metadatos y `DELETE /api/provider-credentials/:id` revoca la credencial. El runner local realiza la inferencia con Pi y admite OpenCode Go y Zen, OpenAI API, Azure OpenAI, Anthropic API, Gemini API, Vertex AI Express, Groq, xAI, DeepSeek, Mistral, Cerebras, Together, NVIDIA NIM, Fireworks, Hugging Face, MiniMax (internacional y China), Moonshot (internacional y China), Xiaomi, Z.ai y Ant Ling. La disponibilidad y los protocolos de modelos dependen del proveedor y del catálogo incluido; no todos los métodos de autenticación de Pi están implementados. Las pruebas usan respuestas simuladas y no verifican modelos ni facturación de una cuenta real. Consulta `runner/README.md` para los métodos y restricciones.

El formulario sugiere identificadores de una instantánea del catálogo de Pi incluido en el cliente. La lista no confirma que un modelo esté disponible en la cuenta ni que admita las herramientas necesarias; puede diferir del catálogo de un runner de otra versión. Los límites del catálogo solo sustituyen los valores del formulario cuando el usuario lo solicita. Para actualizar la instantánea tras cambiar Pi, ejecuta `node scripts/generate-pi-model-catalog.mjs` desde `client/`; el build web comprueba que no haya quedado desactualizada.

Para desarrollo local, además de las variables de Better Auth, define en `.dev.vars` un `CREDENTIAL_KEY_HEX` aleatorio de 64 caracteres hexadecimales y un `CREDENTIAL_KEY_ID` no secreto. No pongas estos valores en Wrangler ni reutilices los valores de prueba. Si falta la clave o su identificador no coincide con ninguna clave disponible, se impide descifrar las credenciales afectadas. Una configuración de claves inválida impide también guardar credenciales.

Para preparar una rotación, conserva la clave anterior en el secreto `CREDENTIAL_PREVIOUS_KEYS_JSON` como objeto JSON que relaciona cada identificador anterior con su clave hexadecimal y configura una clave activa nueva con un identificador distinto. El runner puede seguir usando credenciales antiguas durante la transición. Cuando un runner obtiene una credencial con una concesión vigente, la API intenta recifrarla con la clave activa; si no puede escribir la actualización, entrega la credencial y la rotación queda pendiente. Cada usuario autenticado también puede llamar `POST /api/provider-credentials/rotate` desde el mismo origen: recifra hasta 50 credenciales activas por petición y devuelve `{rotated, failed}`. Si devuelve `nextCursor`, envíalo como `{cursor: nextCursor}` en la siguiente petición y continúa hasta que no aparezca. Después vuelve a comenzar sin cursor para reintentar credenciales fallidas; estas no impiden procesar las posteriores. Los errores incluyen claves ausentes, datos dañados y cambios concurrentes; no se muestran secretos. Al abrir una sesión verificada, la web solicita la rotación de hasta 100 lotes de esa cuenta y se detiene al cerrar o cambiar la sesión; los errores se intentan de nuevo al abrirla. La operación no recorre automáticamente las cuentas inactivas ni tiene interfaz de administración. Antes de retirar una clave anterior hay que comprobar en D1 los `key_id` de todas las credenciales activas, atender las cuentas inactivas y conservar las claves necesarias para restaurar respaldos anteriores. Coordina el cambio de configuración de todas las instancias antes de crear o recifrar datos con la nueva clave. Perder una clave necesaria hace inaccesibles las credenciales correspondientes. Este mecanismo necesita revisión y un procedimiento operativo completo antes de producción.

Un trabajo selecciona la credencial mediante `credentialId` separado del `payload`. `POST /api/runner/jobs/:id/credential` entrega la credencial al runner con la concesión activa. `POST /api/runner/jobs/:id/files/:fileId` entrega solo un documento cuyo ID está en `payload.fileIds` y pertenece al proyecto. Ambos comprueban usuario, runner, tarea, concesión, caducidad y revocación. Los secretos recibidos se retiran de los resultados exactos y los errores de tareas con credenciales se presentan genéricamente.

La tarea `tender-chat.send` requiere `credentialId`, `payload.question`, `payload.fileIds` y `payload.dataProcessingConsent: true`. La interfaz advierte sobre las variantes Contributor y solicita consentimiento; el usuario debe revisar las condiciones del modelo seleccionado antes de enviar documentos. El handler admite texto, DOCX y PDF con texto; no incluye OCR. Una consulta puede referirse a una respuesta terminada del mismo proyecto y los mismos documentos mediante `previousJobId`. El servidor recupera hasta diez pares anteriores (máximo 60.000 caracteres) y los entrega al runner como contexto, sin aceptar historial arbitrario del navegador.

Cuando Pi devuelve preguntas sugeridas, la web las presenta para la última respuesta si siguen seleccionados los mismos documentos, no hay consultas activas y está habilitada la continuación. Elegir una pregunta solo la coloca en el editor: el usuario conserva el control del envío y del consentimiento.

`DELETE /api/projects/:id/chat-history` permite iniciar una nueva conversación después de confirmar la operación. Solo elimina las tareas del chat web del proyecto; conserva los documentos, los demás trabajos y el historial importado. La operación requiere la sesión propietaria y el mismo origen, y devuelve 409 si hay una consulta en cola o en ejecución. La creación de una continuación comprueba de forma atómica que su respuesta anterior siga disponible.

## Oferta económica web

`GET /api/projects/:id/economic-offer` obtiene el borrador del propietario y su cálculo. `PUT` guarda `{draft,version}`; usa versión 0 para crear y la versión devuelta para actualizar. Si otra sesión guarda primero, responde 409 y el cliente conserva sus cambios sin sobrescribir el borrador. Los borradores incompletos se guardan aunque todavía no sea posible calcularlos. `POST /api/projects/:id/economic-offer/export` genera el CSV con las mismas reglas de escritorio. El cálculo aritmético reutiliza el servicio existente en el Worker, sin inferencia y sin habilitar runners alojados.

## Oportunidades SECOP

`POST /api/secop/search` consulta los conjuntos públicos de SECOP I, SECOP II o contratos en datos.gov.co, únicamente cuando el usuario inicia una búsqueda. Reutiliza el constructor de consultas y el mapeo del cliente; las pruebas interceptan la fuente y no hacen llamadas externas. `POST /api/projects/from-secop` crea un proyecto con los metadatos de la oportunidad, con prevención de duplicados por usuario, fuente e identificador. `GET /api/projects/:id/secop` devuelve los metadatos solo a su propietario. Para proyectos SECOP II con portafolio, `GET /api/projects/:id/secop/documents` consulta el índice oficial y comunica resultados parciales o truncados. `POST /api/projects/:id/secop/documents/:documentId/import` verifica pertenencia, descarga desde el endpoint fijo de SECOP y guarda el archivo en R2 sin duplicados. Admite PDF, DOC, DOCX, XLS y XLSX hasta 50 MB. Los ZIP verificados en el portafolio se importan mediante una tarea del runner, con límites de extracción y publicación idempotente de los documentos compatibles. La descarga directa se transfiere por partes de 5 MiB a R2 con staging y requiere pruebas de carga en Cloudflare antes de producción; la importación ZIP no se ha verificado contra SECOP real ni en todas las plataformas.

## Seguimiento de licitación

`GET/PUT /api/projects/:id/workflow` consulta o actualiza la etapa; los recursos `tasks` y `requirements` permiten listar, crear, actualizar y eliminar tareas y requisitos manuales. Las mutaciones requieren sesión, origen y versión vigente para evitar sobrescribir cambios de otra sesión. La matriz de requisitos guardados se descarga en CSV o Excel mediante `GET /api/projects/:id/workflow/requirements/export?format=csv|xlsx&language=es|en`, reutilizando los formatos de escritorio. Cada requisito con fuente guardada puede compararse con un dato RUP revisado. La comparación conserva la regla y el PDF de origen, marca cambios posteriores en sus fuentes y se incluye en la exportación; no modifica la valoración humana. Las sugerencias de Pi se muestran con su cita y fuente; cada una se agrega por decisión del usuario como requisito pendiente, con prevención de duplicados y control de cambios de fuentes.

## Plan técnico: edición manual

`GET /api/projects/:id/technical-plan` devuelve el árbol y su versión. Los recursos `nodes`, `nodes/:nodeId`, `nodes/:nodeId/content` y `nodes/:nodeId/move` permiten crear, editar, eliminar, guardar contenido y cambiar el orden entre hermanos. El servidor asigna UUID estables y calcula los números desde la posición; cada mutación comprueba una versión y se ejecuta como lote atómico en D1. Ordenar conserva el contenido. Editar metadatos invalida el contenido del nodo afectado; agregar el primer hijo invalida el contenido del padre, y eliminar una rama elimina sus descendientes. La interfaz pide confirmación antes de las operaciones que borran contenido. La tarea `technical-plan.generate-section` solicita un borrador revisable para un capítulo hoja con la versión y documentos elegidos. El runner obtiene el contexto con su concesión, y `POST /api/projects/:id/technical-plan/nodes/:nodeId/apply-job` aplica únicamente un resultado exitoso del mismo proyecto y versión. La tarea `technical-plan.export-word` exporta la versión guardada con el formato predeterminado mediante un runner local preparado; el archivo se sube a R2 y solo su propietario puede descargarlo una vez finalizada la tarea. También existen generación por lotes, importación desde escritorio y plantillas de exportación; consulta `runner/README.md` para sus condiciones y límites. La paridad completa con escritorio aún requiere verificación funcional.


## Archivos de trabajos

El runner sube el Word al endpoint de la concesión activa y el propietario descarga el resultado de la tarea terminada. La carga admite hasta 25 MiB, identifica el contenido por SHA-256 y acepta reintentos idénticos; otro contenido para la misma tarea se rechaza. El resultado de la cola contiene solo el identificador y las advertencias. El propietario puede eliminar desde la tarea terminada el archivo generado, incluso si la tarea terminó cancelada, interrumpida o fallida después de la subida. La eliminación se marca antes de retirar el objeto de R2; si la limpieza falla, queda pendiente y puede reintentarse desde la interfaz. Falta una política de retención automática y un proceso de limpieza de objetos huérfanos antes de producción. Una caída entre la carga y la escritura del resultado en la bandeja local puede dejar una tarea interrumpida, que no se reejecuta automáticamente.

## Certificado RUP y datos revisados

En «Modelo y RUP» se puede guardar un PDF de hasta 25 MiB, abrirlo, registrar su fecha de expedición y agregar, corregir o eliminar datos revisados con una página válida. La API verifica que el PDF se pueda abrir y tiene al menos una página; no verifica la autenticidad ni la vigencia del certificado. El RUP actual y sus datos pertenecen a la cuenta, se guardan con versiones y rechazan cambios simultáneos obsoletos. Al sustituirlo, las copias anteriores permanecen en R2 para conservar las fuentes de futuras comparaciones; todavía falta una interfaz de retención y eliminación de esas copias.

El usuario puede solicitar un análisis con Pi a su runner local usando una credencial de proveedor admitida y consentimiento explícito. El runner extrae texto seleccionable, comprueba cada cita contra la página y devuelve sugerencias para revisión humana; no guarda los datos automáticamente. El análisis de PDF escaneados mediante OCR y la separación por empresa todavía no están implementados en la web. El RUP y los certificados del escritorio se pueden importar con el runner; consulta sus requisitos en `runner/README.md`.


## Análisis RUP por cuenta

`POST /api/rup/analyses` crea una tarea idempotente asociada a la cuenta, versión del certificado y credencial; `GET` enumera las tareas y `POST /api/rup/analyses/:id/cancel` las cancela. La concesión limita el acceso al PDF y la credencial al runner asignado. El runner comprueba otra vez la versión tras el análisis y devuelve solo citas verificadas; el usuario debe revisarlas antes de incorporarlas. La interfaz impide copiar sugerencias cuya versión del certificado ya no sea la actual, y el servidor exige la versión vigente al guardar los datos revisados. Se requiere una política de retención para el historial de análisis antes de producción.

El editor de Word guarda una copia de recuperación separada en R2 cuando hay cambios sin guardar; su referencia y revisión se conservan en D1 mediante la migración `0164`. La copia no sustituye el Word guardado ni confirma la revisión. Al volver al enlace del editor se restaura si corresponde a la misma versión; si el Word cambió en otra sesión, se ofrece la copia anterior para descargar. El guardado explícito y el descarte retiran la copia correspondiente, y el borrado del proyecto o de la exportación programa la limpieza del archivo. Esta función necesita conectividad: la interfaz avisa si no consigue guardar la copia y conserva la advertencia de cambios sin guardar.


## Sugerencias de requisitos

`requirements.suggest` utiliza los documentos seleccionados y una credencial de proveedor admitida del usuario. La inclusión de datos revisados del RUP es opcional y requiere seleccionarla en el consentimiento; los demás datos de empresa no se envían. Pi utiliza herramientas de lectura, y el runner descarta citas que no aparezcan literalmente en la fuente y referencias inexistentes. Los documentos sin texto se indican por separado. Una sugerencia solo se agrega por decisión del usuario y mientras sus fuentes sigan vigentes; se guarda como pendiente, sin determinar cumplimiento. El historial todavía requiere una política de retención antes de producción.

La prueba local del sitio `node --test test-assets/site.test.mjs` usa Wrangler con una base temporal y la web compilada. Comprueba registro de dos cuentas, creación de proyecto, carga idempotente y aislamiento de archivos, emparejamiento y entrega de una credencial de prueba bajo concesión. No ejecuta inferencia ni reemplaza una revisión visual del navegador o una prueba del servicio Cloudflare real.

### Acceso público

Registro y recuperación están desactivados por defecto en el login y sus rutas HTTP. Para habilitarlos en el entorno del Worker:

```dotenv
AUTH_ALLOW_REGISTRATION=true
AUTH_ALLOW_PASSWORD_RECOVERY=true
```

La recuperación también requiere `EMAIL` y `AUTH_EMAIL_FROM`. Omitir las variables o usar `false` mantiene las funciones desactivadas. El superadministrador por entorno y las cuentas existentes pueden seguir iniciando sesión.

### Descargas del conector

`RUNNER_DOWNLOAD_WINDOWS_URL`, `RUNNER_DOWNLOAD_MACOS_ARM64_URL` y `RUNNER_DOWNLOAD_MACOS_X64_URL` deben apuntar a instaladores HTTPS publicados y verificados para el sistema indicado. Si no se configuran, la pantalla informa que el instalador no está disponible; nunca ofrece un enlace ficticio. El enlace común `RUNNER_DOWNLOAD_MACOS_URL` solo debe configurarse si sirve para ambas arquitecturas. Los instaladores autónomos y su compilación se documentan en `connector/README.md`.
