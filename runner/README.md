# Runner local de Savia: emparejamiento inicial

Esta utilidad es una primera pieza del runner. Puede emparejarse, comprobar conexión y ejecutar trabajos compatibles; admite el cálculo de oferta económica y una primera consulta de licitación con Pi. Aún no está lista para producción.

Con la API local en marcha y un código generado por `POST /api/runner-pairings`, ejecuta:

```sh
node runner/cli.mjs pair --server http://127.0.0.1:8788 --name "Mi equipo"
```

Pega el código por entrada estándar y pulsa Enter. También se admite una entrada por tubería terminada en EOF. A continuación, `node runner/cli.mjs heartbeat` comprueba la conexión. La credencial se guarda en `~/.savia/runner.json`; en macOS/Linux se establece modo 0600. Para pruebas se puede usar `--config` para elegir otra ubicación. Windows utiliza los permisos de la cuenta y del directorio del usuario: aún falta integrar una protección mediante el almacén seguro del sistema.

El servidor requiere HTTPS salvo para pruebas en `localhost`, `127.0.0.1` o `::1`. El código es válido por cinco minutos y se puede canjear una sola vez. Si se revoca el runner, solicita un código nuevo y vuelve a emparejarlo. El proceso no realiza conmutación a servicios alojados.

## Ejecutar trabajos locales

En Conexión e IA se configura por equipo un máximo de uno a cuatro agentes simultáneos; el valor inicial es uno. Cada tarea se ejecuta en un entorno aislado y conserva su propia concesión, consola y copia recuperable. Reducir el límite deja terminar las tareas ya iniciadas. La cola indicada en la web es compartida por la organización; los contadores del equipo reflejan las tareas asignadas y completadas que aún conserva el historial. El cambio requiere una versión del conector compatible.

`node runner/cli.mjs run` consulta continuamente la cola de la cuenta y reclama solo los tipos implementados. `node runner/cli.mjs run-once` procesa como máximo un trabajo. Admite `economic-offer.calculate`, que utiliza el cálculo existente del cliente de escritorio, `tender-chat.send`, que usa Pi y el servicio de consulta existente, `technical-plan.generate-section`, que prepara un borrador revisable para un capítulo con los mismos documentos y runtime, `technical-plan.export-word`, que usa el helper OpenXML preparado para generar un archivo Word, `rup.analyze`, que extrae texto del certificado y revisa las citas propuestas por Pi, y `requirements.suggest`, que propone requisitos citados desde los documentos seleccionados. Los trabajos de otros tipos permanecen en espera. Para detener el proceso, usa Ctrl-C o SIGTERM.

Las tareas de texto admiten OpenCode Go y Zen, OpenAI API, Azure OpenAI, Anthropic API, Gemini API, Vertex AI Express, Groq, xAI, DeepSeek, Mistral, Cerebras, Together, NVIDIA NIM, Fireworks, Hugging Face, MiniMax (internacional y China), Moonshot (internacional y China), Xiaomi, Z.ai y Ant Ling, con las restricciones de modelo y autenticación indicadas más abajo. No están implementados todos los métodos de autenticación de Pi. Para Claude se usa el protocolo Messages nativo de Pi y una clave de API de Anthropic asociada a un espacio de trabajo; no se admiten credenciales OAuth de Claude Code. OpenAI API requiere su propia clave y cuota, y el acceso por suscripción de ChatGPT no está implementado. La integración xAI usa Responses con `store: false` y conserva el razonamiento cifrado durante la sesión. Las pruebas de proveedores usan respuestas simuladas y no verifican modelos ni facturación en una cuenta real.

Cada credencial permite indicar la ventana de contexto y la salida máxima del modelo. Si no se configuran, se conservan los valores anteriores de 400.000 y 16.384 tokens; consulta los límites reales del modelo antes de usarlo. Para cambiar estos valores se puede retirar la credencial y crear otra. Los límites se entregan al runner junto con la credencial de la tarea.

La concesión se renueva mientras la tarea está activa y durante la entrega. Los fallos temporales de renovación se reintentan dentro del plazo seguro; si la concesión se pierde, el agente se interrumpe y la tarea no se vuelve a ejecutar automáticamente. Antes de enviar un resultado, el runner intenta guardar una copia cifrada temporal junto a su configuración; al arrancar reenvía las pendientes antes de reclamar otra tarea. La clave se deriva del token del runner y la copia se elimina al recibir confirmación. Si el disco no permite guardar la copia, el runner avisa e intenta enviar el resultado igualmente.

Una concesión vencida o cancelada sigue sin aceptar resultados nuevos. En ese caso se conserva la copia cifrada para recuperación manual. `node runner/cli.mjs outbox-list` muestra los identificadores y estados; `node runner/cli.mjs outbox-export --job ID --output /ruta/absoluta/nueva.json` exporta el resultado sin la concesión a un archivo que no debe existir. Esa exportación contiene datos del usuario en texto legible; protégela como corresponda. El archivo final se publica después de completar la escritura, sin reemplazar uno existente. Un cierre forzado puede dejar un archivo temporal legible en la carpeta de destino. Después de comprobarla, `node runner/cli.mjs outbox-discard --job ID --state rejected` retira la copia cifrada; el estado también puede ser `pending`. En macOS/Linux los archivos se crean con permisos 0600; Windows usa los permisos de la cuenta y el directorio. Para no perder la clave, el runner impide volver a emparejar mientras existan copias pendientes o rechazadas. Detén todas las instancias de esa configuración antes de volver a emparejar. Las copias recuperables admiten hasta 5.000.000 bytes de resultado serializado. Si un resultado excede ese límite, el runner avisa e intenta entregarlo, pero no conserva una copia local; las etapas técnicas que exigen copia se detienen. Si se pierde o reemplaza el token, o se modifican el identificador del runner o la dirección del servidor en la configuración, las copias asociadas no se pueden descifrar.

Para construir una carpeta preliminar independiente en el sistema de destino, después de instalar y verificar las dependencias conforme a `DEPENDENCY_POLICY.md`, prepara el helper para esa plataforma con `node client/scripts/prepare-openxml-helper.cjs --platform PLATAFORMA --arch ARQUITECTURA` y ejecuta desde la raíz `pnpm run build:runner --output /ruta/absoluta/nueva`. El empaquetador exige el helper preparado y lo incorpora con su SHA-256 en el manifiesto. La carpeta debe no existir; la preparación usa el almacén local sin descargar paquetes y comprueba las herramientas incluidas. Admite herramientas preparadas para macOS arm64/x64, Windows x64 y Linux arm64/x64. La salida incluye instrucciones y requiere Node 22.13 o posterior, pero todavía no es un instalador ni está validada en todos los sistemas. En Linux se requieren además glibc e ICU para el helper; las pruebas utilizaron la imagen oficial de dependencias de .NET 10. Si la caché local de pnpm no incluye los metadatos completos, añade `--prepare-cache` al comando de construcción: esta opción usa la red explícitamente, verifica la antigüedad del lockfile y prepara la caché sin ejecutar scripts de dependencias; la construcción final continúa sin conexión. Sin esa opción, la construcción no consulta la red. El paquete actual incluye dependencias de producción del cliente y es grande. No contiene la configuración ni el token del usuario.

El contexto del manejador ofrece `getCredential()` y `getFile(id)` para la concesión actual. Solo se autoriza la credencial seleccionada por el usuario y los documentos seleccionados para ese trabajo. La consulta de licitación las utiliza para proporcionar a Pi la credencial y los documentos autorizados. Los resultados eliminan coincidencias exactas de secretos conocidos; esta medida no sustituye una revisión de privacidad de los prompts y respuestas ni detecta transformaciones de las claves.

## Consulta de licitación con Pi

`tender-chat.send` requiere `credentialId`, una pregunta, `fileIds` del mismo proyecto y `dataProcessingConsent: true`. El consentimiento debe obtenerse mostrando al usuario las condiciones de uso de datos del modelo; la variante Contributor puede permitir usar solicitudes y respuestas para entrenamiento. El handler usa el proveedor elegido, el parser local y Pi existentes, y elimina los temporales al terminar. Admite texto UTF-8, DOCX, XLS, XLSX y PDF con texto seleccionable. También admite DOC y WPS mediante un conversor local compatible; puede requerir LibreOffice. No incorpora OCR para PDF escaneado. Cada consulta inicia una sesión Pi nueva; el servidor suministra hasta diez turnos anteriores como contexto cuando el usuario continúa con los mismos documentos. Si el agente solicita una aclaración durante la tarea, la pregunta se muestra en la web y la ejecución espera la respuesta del usuario. Si el proceso se cierra a la fuerza, los espacios temporales identificados que tengan al menos una hora y pertenezcan a un proceso ya terminado se eliminan al iniciar `run` o `run-once`; los espacios antiguos que no tienen esa identificación no se eliminan automáticamente.

Desde la raíz, `pnpm run test:runner` prueba Pi y el parser con respuestas simuladas; no llama a un proveedor de IA.

## Borrador de capítulo

`technical-plan.generate-section` recupera el título y descripción del capítulo solo mientras su concesión y la versión del plan sigan vigentes. Usa el parser local y Pi con el proveedor elegido para producir un borrador Markdown basado en los documentos seleccionados. La aplicación no modifica el capítulo automáticamente: el usuario revisa y aplica el resultado, y el servidor rechaza la aplicación si el plan cambió. Es un flujo inicial sin las fases completas de planificación, ilustraciones ni exportación del escritorio.

## Trabajo en curso: conversión del plan a Word

El adaptador `technical-plan-export.mjs` usa el ensamblador y el helper OpenXML del escritorio en un espacio temporal aislado. La web permite seleccionar el formato de cuenta o una plantilla de formato y la tarea conserva esa selección; el runner incorpora imágenes disponibles y valores de plantilla del proyecto. La prueba con el helper real verificó en macOS ARM64 texto, orientación, imágenes PNG y WebP y limpieza temporal. Siguen pendientes las pruebas en los demás sistemas.

La prueba con el helper preparado se ejecuta con `SAVIA_TEST_OPENXML=1 SAVIA_OPENXML_TEST_EXE=/ruta/absoluta/openxmlhelper node --test runner/test/technical-plan-export.test.mjs`. Usar el binario preparado evita requerir el SDK durante la prueba. La suite ordinaria también verifica limpieza y errores con un helper simulado.


## Análisis RUP con Pi

La tarea `rup.analyze` requiere una credencial de proveedor admitido y consentimiento explícito. El runner extrae el texto seleccionable por página, entrega las páginas a Pi con herramientas de solo lectura y verifica la cita y el valor antes de devolver sugerencias. Un PDF sin texto seleccionable requiere revisión manual; no se incluye OCR. Los resultados se guardan para revisión y no modifican automáticamente los datos revisados. Si cambia el certificado durante la ejecución, el resultado se rechaza.


## Sugerencias de requisitos

`requirements.suggest` procesa los documentos seleccionados localmente y usa Pi con el proveedor elegido. Los datos revisados del RUP se incluyen únicamente cuando el usuario los selecciona y autoriza. Las citas y los identificadores propuestos se contrastan con las fuentes antes de devolverlos; la aceptación se hace por separado desde la web y conserva el estado pendiente. Los documentos incompatibles o sin texto se indican en el resultado, y los PDF escaneados no reciben OCR en este flujo.

## Biblioteca de conocimiento

`knowledge.analyze` descarga exclusivamente el documento autorizado de la biblioteca, extrae el texto localmente y usa Pi con la credencial de proveedor elegida. Requiere consentimiento explícito. Admite TXT, Markdown, DOCX, XLS, XLSX y PDF con texto seleccionable; DOC y WPS pueden requerir LibreOffice u otro conversor local. El análisis rechaza textos de más de 300.000 caracteres en lugar de recortarlos. Las citas que no aparecen literalmente en el texto extraído se descartan. El usuario revisa y acepta los resultados antes de incorporarlos al índice de búsqueda. Los resúmenes generados deben verificarse junto con sus citas. Eliminar el documento cancela el acceso a su tarea y retira resultados e índice asociados.

Los borradores de capítulos pueden incluir, con autorización específica, entradas aceptadas de la biblioteca. El runner recibe únicamente los extractos seleccionados y usa los hechos globales aprobados con prioridad. Las revisiones de las entradas se comprueban al crear la tarea, preparar su contexto y aplicar el borrador. El usuario también puede autorizar que Pi consulte el texto completo de los originales asociados; el runner lo extrae localmente y limita el total a un millón de caracteres.

## Importación inicial desde respaldo de escritorio

Con el runner conectado, `node runner/cli.mjs capture-account-components --output /ruta/absoluta/nueva` captura en subcarpetas las preferencias, perfil de empresa, imágenes, RUP, certificados, formato de exportación, biblioteca de conocimiento, seguimientos PAA, experiencia y viabilidad. Es una captura **parcial**: no incluye proyectos, credenciales ni todos los demás datos, y sus componentes se leen en momentos diferentes. Los archivos no están cifrados. La carpeta de salida debe ser nueva; si una captura falla, las anteriores se conservan y no se publica `index.json`.

Para capturar los proyectos de la cuenta vinculada en otra carpeta nueva, usa `node runner/cli.mjs capture-account-projects --output /ruta/absoluta/nueva`. Se capturan hasta 10.000 proyectos con el transporte parcial de cada proyecto y se compara el inventario al final. Una falla o cambio detectado conserva las capturas terminadas sin publicar el índice; la comparación no garantiza una instantánea atómica. Para recuperar un conjunto terminado en la cuenta vinculada al runner usa `node runner/cli.mjs restore-account-projects --snapshot /ruta/absoluta/captura`. Comprueba primero la integridad del conjunto, recupera los proyectos secuencialmente y muestra los IDs de origen y destino. Una interrupción puede dejar proyectos recuperados; repetir utiliza los recibos existentes y no sustituye las ediciones posteriores. Si tienes la captura de la biblioteca compartida, añade `--knowledge-snapshot /ruta/absoluta/biblioteca`; deben coincidir las fuentes referenciadas. Una captura sin índice debe recuperarse por proyecto con `restore-project-components`. La captura no está cifrada y no incluye credenciales ni todos los datos.

Para recuperar un conjunto terminado, conecta el runner a la cuenta de destino, consulta su revisión con `node runner/cli.mjs read-account-preferences` y ejecuta `node runner/cli.mjs restore-account-components --snapshot /ruta/absoluta/captura --expected-revision N`. La operación comprueba primero la integridad de los componentes y la revisión, muestra el resultado de cada uno y aplica las preferencias al final, sustituyendo las del destino. Conserva las reglas de conflicto y de elementos retirados de cada restaurador; puede dejar cambios parciales si ocurre un error. Si se interrumpe, consulta de nuevo la revisión antes de repetir y revisa los resultados. Una captura incompleta sin índice se recupera por subcarpetas mediante los comandos `restore-account-...` correspondientes. Esto no restaura una cuenta completa.

`node runner/cli.mjs inspect-backup --backup /ruta/absoluta/respaldo.savia` verifica el archivo y muestra los planes disponibles sin publicar su contenido. Con el runner emparejado, `node runner/cli.mjs import-plan --backup /ruta/absoluta/respaldo.savia --project ID` crea un proyecto web nuevo preservando las identidades, jerarquía y texto del plan seleccionado. Los reintentos de ese mismo archivo y plan son idempotentes. La función también transfiere originales de licitación disponibles e informa los que falten; un reintento continúa sin duplicados. Los mayores de 25 MiB se envían por flujo y los mayores de 50 MiB por partes. El formato del respaldo de escritorio conserva su límite total de 256 MiB de contenido y se lee en memoria; no admite originales de 1 GiB. Importa los grupos de hechos globales y requiere revisarlos en la web antes de utilizarlos; confirmar esa revisión conserva el texto de los capítulos. Los hechos existentes en la web no se reemplazan. Los límites de importación son 500 grupos y tres millones de caracteres por conjunto; si se exceden se informa un error. El respaldo no se modifica; consulta los apartados siguientes para conocer el alcance de cada importación. Para crear el respaldo cierra Savia y usa `list-desktop-companies --user-data /ruta/absoluta` seguido de `create-backup --user-data /ruta/absoluta --company ID --output /otra/ruta/respaldo.savia`. El archivo contiene datos empresariales sin cifrar y no sobrescribe un destino existente. La interfaz gráfica de captura sigue pendiente.

Los documentos requeridos de cada requisito se transfieren con su estado. Para vincular automáticamente un certificado o RUP, importa también ese documento desde el mismo respaldo con `import-certificates` o `import-rup` y repite `import-plan` o `import-saved-tenders`. Solo se enlazan soportes que sigan sin modificar y que tengan un recibo que identifique el documento; el RUP debe seguir siendo el actual. Los vínculos sin prueba o procedentes de importaciones anteriores sin esos recibos quedan como no disponibles y pueden seleccionarse manualmente en la web. El resultado informa conflictos y el número de soportes cuyo requisito falta. La revisión del documento sigue siendo responsabilidad del usuario.

El runner identifica y guarda imágenes PNG, JPEG, GIF y WebP referenciadas y disponibles de hasta 25 MiB; informa las ausentes, externas, inseguras o de formato no compatible. La vista previa del capítulo muestra las imágenes guardadas del proyecto y no carga imágenes externas. La exportación Word recupera las imágenes referenciadas desde la nube y convierte WebP estático a PNG; si no puede incorporar una imagen, incluido WebP animado, conserva el texto y muestra un aviso.

Si se retira de la web un documento importado, repetir la importación no lo restaura: el resultado lo enumera en `removedDocuments`. Para incorporarlo de nuevo, súbelo explícitamente al proyecto.

Cuando se puede identificar el proceso asociado, la importación también transfiere su etapa, tareas y requisitos. Los capítulos que referencian requisitos mantienen el vínculo con sus nuevos identificadores web. Un proyecto que ya tenga seguimiento web no se sobrescribe: la importación informa el conflicto. Las tareas de generación aún no se migran.

El borrador de oferta económica del proceso asociado también se importa, incluso si todavía contiene campos incompletos. Si ya existe una oferta en la web, no se reemplaza. Los reintentos del mismo respaldo conservan las ediciones posteriores.

Para transferir el certificado RUP actual y sus datos revisados a la cuenta web, ejecuta `node runner/cli.mjs import-rup --backup /ruta/absoluta/respaldo.savia`. El comando requiere un runner emparejado y un PDF presente y legible en el respaldo; no reemplaza un certificado ya configurado en la web. Los datos se vinculan al PDF que se está importando y sus páginas deben existir. La inspección indica si hay un RUP y cuántos datos contiene, sin mostrar sus valores.

Las comparaciones RUP del plan se importan como registros históricos separados, con sus PDF cuando están disponibles. No modifican la valoración actual y requieren revisión de fuentes. Si el requisito original no tiene una correspondencia registrada, el histórico permanece visible sin vínculo; esto incluye importaciones previas a la creación de los mapas. Los PDF históricos se conservan como fuentes de las comparaciones, no como certificados actuales de la cuenta.

Para trasladar la biblioteca de imágenes, ejecuta `node runner/cli.mjs import-images --backup /ruta/absoluta/respaldo.savia`. Se conservan nombre, fecha y orden; el resultado informa originales ausentes, inseguros, vacíos, mayores de 25 MiB o incompatibles. Esos registros permanecen visibles en la web y permiten adjuntar un original posteriormente. Comprueba que corresponda a la imagen histórica. Repetir la importación no recrea imágenes eliminadas ni reemplaza originales adjuntados. Las imágenes del plan se gestionan por su propio protocolo.

`inspect-backup` también informa si hay una revisión de duplicados, cuántos archivos contiene y cuántos originales y textos extraídos no están disponibles. Importa sus resultados y archivos disponibles con `node runner/cli.mjs import-duplicate-check --backup /ruta/absoluta/respaldo.savia`. Si la transferencia se interrumpe, repite el comando para continuar; los archivos distintos no reemplazan los ya transferidos. La web presenta los resultados como históricos y no reanuda las tareas. Los originales elegidos fuera del espacio de Savia pueden no estar incluidos en la copia y se pueden adjuntar después de comprobar su identidad. Al eliminar una revisión, repetir la importación informa que fue retirada y no la recrea. Para una revisión nueva, carga los documentos en un proyecto, asígnalos como pliegos u ofertas y ejecuta la revisión desde ese proyecto con el runner activo. El informe completo se descarga en JSON y puede exportarse a Excel desde la vista de resultados; Excel limita el tamaño del texto por celda. Si el informe supera 25 MiB, reduce la cantidad de documentos.

Para trasladar una revisión de causales de rechazo, usa `node runner/cli.mjs import-rejection-check --backup /ruta/absoluta/respaldo.savia`. Se transfieren los hallazgos, textos procesados e imágenes disponibles; el comando informa cuántos archivos faltan. Repetirlo continúa una transferencia interrumpida y no recrea una revisión eliminada. Los resultados son históricos y no reanudan tareas.

Para una revisión nueva, selecciona pliegos y ofertas en un proyecto, configura una credencial de proveedor admitido y autoriza el procesamiento. Puedes extraer y revisar las causales antes de ejecutar las comprobaciones de rechazo, ortografía o lógica. El runner usa Pi y el informe completo se guarda para consulta y descarga; si una sección falla, se indica en el informe.

Para importar copias de licitaciones guardadas sin plan asociado, ejecuta `node runner/cli.mjs import-saved-tenders --backup /ruta/absoluta/respaldo.savia`. Crea proyectos para las copias SECOP y locales, conserva su resumen, análisis, texto extraído y referencias oficiales como datos históricos, y transfiere su seguimiento, tareas, requisitos, oferta y comparaciones cuando están disponibles. El texto extraído no equivale a los archivos originales. El resultado identifica copias vinculadas a planes, asociaciones ambiguas, conflictos, datos incompatibles y registros retirados; no reemplaza una licitación existente. Si falta una instantánea no se presume que las copias restantes estén desvinculadas. Cada copia histórica admite hasta tres millones de caracteres; conserva el respaldo original para datos que excedan ese límite o no puedan importarse.

Al importar un plan con `import-plan`, el runner también intenta trasladar su licitación SECOP guardada y sus avisos si el respaldo contiene un vínculo inequívoco. `secopStatus` informa conflictos, asociaciones retiradas o datos incompatibles; no se reemplazan asociaciones ni seguimientos existentes. El comando no consulta SECOP durante la importación. Las licitaciones guardadas sin un plan asociado aún no se transfieren con este comando.

Para importar los planes PAA seguidos y sus avisos, ejecuta `node runner/cli.mjs import-paa --backup /ruta/absoluta/respaldo.savia`. Las revisiones y estados de los avisos se conservan; el comando no consulta SECOP ni reemplaza un seguimiento existente. El resultado informa los identificadores en conflicto, los planes previamente retirados y los avisos huérfanos que no se pudieron asociar. Los reintentos no recrean planes retirados. Mantén el respaldo si contiene avisos huérfanos.

Para importar los registros de certificados de la empresa, ejecuta `node runner/cli.mjs import-certificates --backup /ruta/absoluta/respaldo.savia` con el runner emparejado. Cada registro conserva sus campos históricos y los reintentos no reemplazan ediciones ni recrean certificados eliminados. `inspect-backup` muestra las cantidades de certificados e imágenes sin revelar su contenido. El resultado informa `importedImages`, `removedImages` y `missingImages`; este último enumera identificadores y motivos de archivos ausentes, inseguros, vacíos, demasiado grandes o de formato incompatible. Conserva el respaldo para recuperar cualquier archivo no transferido. Los registros con valores de vigencia antiguos pueden necesitar corrección antes de editarse en la web.

Para importar carpetas y originales de la biblioteca de conocimiento, ejecuta `node runner/cli.mjs import-knowledge --backup /ruta/absoluta/respaldo.savia`. Las entradas del escritorio se conservan como históricos consultables separados de los fragmentos aceptados en la web; no se tratan automáticamente como citas literales ni se usan para generación. El resultado informa originales ausentes, fuera del respaldo, vacíos o mayores de 25 MiB; sus entradas históricas también se conservan, pero no se puede descargar ni analizar un original ausente. Los reintentos no recrean archivos ni carpetas retirados por el usuario.

Desde la biblioteca web puedes adjuntar un archivo a un registro cuyo original esté ausente. Comprueba que corresponda al documento histórico: Savia no puede verificarlo. Las entradas importadas siguen siendo históricas y no se aceptan automáticamente como citas.

La inspección también muestra `factGroupCount`, la cantidad de grupos de hechos globales encontrados en cada plan, sin mostrar su contenido. Tras importarlos, revisa sus soportes: el respaldo puede no contener todas las fuentes originales.
