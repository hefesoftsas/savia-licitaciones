# Savia Bidding Toolbox Development Guide (Savia Licitaciones开发说明)

Este documento está dirigido a quienes trabajan en `client/`. El comportamiento de las funcionalidades lo define el código actual; este documento solo conserva las reglas estables que ayudan a localizar código, colaborar entre procesos, reutilizar la interfaz, mantener el estado persistente y completar la verificación.

## Inicio rápido

No existe `package.json` del cliente en la raíz del repositorio. Ejecuta todos los comandos del cliente desde dentro de `client/`:

```powershell
cd client
npm ci             # Install dependencies; postinstall rebuilds native modules for the current Electron
npm run dev        # Start Vite at 127.0.0.1:5173, then open Electron
npm run build      # tsc --noEmit && vite build
```

- La CI usa Node 22. Cuando las compilaciones locales y las de publicación difieran, ajusta primero a esa versión.
- `better-sqlite3` es una dependencia nativa de Electron. Si ves un desajuste de `NODE_MODULE_VERSION`, ejecuta `npm run postinstall`; verifica el ABI con `npm run smoke:electron-native` en lugar de cargar un Store en un proceso Node común.
- El proyecto no tiene un script unificado de lint ni un script de pruebas para todo el proyecto; ejecuta los archivos `*.test.cjs` existentes de forma individual con `node --test <file>` según el alcance de tu cambio.

## Estructura de ejecución

```text
src/main.tsx
├─ Standalone developer window (selected by ?window=...)
└─ AppProviders
   └─ WorkspaceDatabaseGate
      └─ App
         └─ AppShell + AppRouter

Renderer
  └─ window.savia
      └─ electron/preload.cjs
          └─ electron/ipc/*.cjs
              └─ electron/services/*.cjs
                  ├─ SQLite Store / config
                  ├─ Files and export
                  └─ AI / Agent / background tasks
```

- El Renderer es Vite + React + TypeScript ESM; el Main de Electron, el preload, el IPC y los servicios del Main son CommonJS y conservan la extensión `.cjs`.
- La ventana principal habilita `contextIsolation` y deshabilita `nodeIntegration`. El Renderer no importa `electron`, `fs` ni `path`, ni usa `ipcRenderer` directamente; las capacidades locales se exponen de forma uniforme a través de `window.savia`.
- El Renderer se encarga del estado de las páginas y de la orquestación de la interacción; el Main se encarga de la configuración, SQLite, el análisis de archivos, la IA, el Agent, las tareas en segundo plano, la exportación, los complementos y las actualizaciones.
- `WorkspaceDatabaseGate` impide que las páginas de negocio se monten hasta que terminen las comprobaciones de la base de datos, las migraciones y la limpieza del historial; el IPC relacionado con la base de datos también se preregistra como manejadores pendientes/no disponibles.
- `AppRouter` es un despacho de componentes basado en `SectionId`, no un enrutamiento por URL. No añadas páginas siguiendo las convenciones de React Router.

## Dónde va el código

|---|---|

| `src/components/` | Componentes del armazón de la aplicación, actualmente sobre todo `AppShell`, `Sidebar` |
| `src/features/<feature>/` | Páginas de cada funcionalidad y sus componentes dedicados, Hooks, tipos y orquestación ligera del Renderer; crea directorios según la complejidad real, no añadas capas vacías |
| `src/shared/ui/` | Componentes de interfaz compartidos entre funcionalidades y Providers globales de interacción |
| `src/shared/types/` | Tipos compartidos entre funcionalidades, tipos de navegación y tipos del puente `window.savia` |
| `src/shared/prompts/` | Constructores de Prompt que aún se usan en el Renderer |
| `src/shared/utils/`, `src/shared/markdown/` | Utilidades puras compartidas entre funcionalidades y ayudas de renderizado de Markdown |
| `src/styles/` | Tokens, armazón, componentes compartidos y estilos por funcionalidad; `src/styles.css` es el único punto de entrada |
| `electron/main.cjs` | Ventanas, protocolos, ciclo de vida de la aplicación y entrada del Main |
| `electron/preload.cjs` | Puente de la ventana principal; las rutas de archivos arrastrados también se exponen aquí vía `webUtils`; la ventana de configuración de complementos usa un `preload-plugin-config.cjs` separado |
| `electron/ipc/` | Registro de IPC y reenvío de parámetros; `index.cjs` gestiona el ensamblaje de servicios y el ciclo de vida de la base de datos |
| `electron/services/` | Servicios de negocio del Main, Stores e implementaciones de tareas; `agent/`, `pi/`, `doc2markdown/` son subcapas dedicadas |
| `electron/utils/` | Utilidades puras del Main, rutas, registros, colas, edición de texto y limpieza de imágenes importadas |
| `electron/resources/` | Instrucciones del Agent, claves públicas de licencia y atestaciones de compilación empaquetadas en el cliente |
| `vendor/agent-tools/`, `scripts/` | Herramientas de comandos del Agent incluidas y scripts de compilación/verificación |

Principios de ubicación:

- El código que solo usa una funcionalidad se queda en esa funcionalidad; solo se sube a `shared/` cuando aparece una reutilización real entre funcionalidades.
- El código de ejecución en `shared/` no debe depender de las funcionalidades. Los actuales `shared/types/ipc.ts` y `shared/types/index.ts` combinan o reexportan algunos tipos de funcionalidades; este es el límite existente de puente/tipos y no debe extenderse a código compartido que referencie componentes o servicios de funcionalidades.
- Los `services/` del Renderer solo realizan llamadas al puente u orquestación ligera; los flujos que consumen tiempo y la persistencia autoritativa viven en el Main.
- El nuevo IPC de negocio se mantiene simple por defecto. El ensamblaje del ciclo de vida en `ipc/index.cjs` y la orquestación existente de mercado/configuración de complementos en `pluginIpc.cjs` son excepciones; no los copies como plantillas para funcionalidades ordinarias.
- No escribas Prompts dentro de los componentes: los Prompts del Renderer van en `src/shared/prompts/`; los Prompts de tareas en segundo plano del Main viven junto a sus servicios de tarea.

### Añadir una nueva página de menú

Revisa al menos las siguientes ubicaciones:

1. `src/shared/types/navigation.ts`: añade un `SectionId`.
2. `src/app/menuConfig.ts`: configura el menú de primer o segundo nivel.
3. `src/app/AppRouter.tsx`: registra el despacho de la página.
4. `src/components/Sidebar.tsx`: añade el mapeo de iconos para `navigationIcons`.
5. `analytics/dashboard/public/src/pages/traffic.js`: añade el nombre chino a mostrar para la nueva ruta de seguimiento.

Cuando un menú de primer nivel tiene `children`, `AppRouter` usa `shared/ui/SecondaryMenuPage.tsx` para mostrar la entrada de segundo nivel; no implementes menús expandibles en la barra lateral. La página de ajustes es una entrada separada al final de la barra lateral.

## Colaboración entre Renderer y Main

Al añadir o modificar una API del puente, actualiza la cadena completa:

1. Implementa la capacidad o la operación del Store en `electron/services/`.
2. Registra el canal en el `electron/ipc/*Ipc.cjs` correspondiente y conecta las dependencias en `electron/ipc/index.cjs`.
3. Si el canal depende de la base de datos del espacio de trabajo, añádelo también a `workspaceDatabaseChannels` en `index.cjs` para que no se omita ni se registre dos veces antes de que la base de datos esté lista.
4. Expón el método o el evento en `electron/preload.cjs`.
5. Sincroniza los tipos de parámetros, valores de retorno y eventos en `src/shared/types/ipc.ts`; la declaración global referencia ese tipo desde `src/vite-env.d.ts`.

Otras convenciones:

- Las API de eventos `onXxx` deben devolver una función para cancelar la suscripción; llámala cuando el efecto de React se desmonte.
- Las páginas de tareas gestionadas primero leen la instantánea del Store, luego se suscriben a `tasks.onTaskEvent()` y después llaman a `tasks.getActiveTasks()`; el último paso vuelve a suscribirse y reproduce las tareas activas, evitando el caso en que el primer evento se dispare antes de registrar el listener.
- La semántica de parche del IPC es "presencia de campo": un campo ausente significa conservar, un campo presente significa aplicar ese valor; `undefined`, `null` o las colecciones vacías suelen usarse para limpieza explícita, según defina cada Store. Al fusionar parches en el Renderer, usa `hasOwnProperty`; no uses comprobaciones de veracidad.
- Las interfaces de comandos pueden devolver `void`, una entidad o un parche parcial; no supongas que cada escritura devuelve el espacio de trabajo completo. Llama explícitamente a `load*` / `get*` / `list*` cuando necesites el estado completo.
- Un `File` de navegador obtenido por arrastrar y soltar se convierte a ruta local vía `window.savia.file.getPathForFile(file)`; no leas el no estándar `file.path`.
- Los enlaces externos pasan por `window.savia.openExternal()`; las imágenes importadas localmente y las generadas usan los `savia-asset://imported-images/...` y `savia-asset://generated-images/...` registrados por el Main. No expongas rutas `file://` al Renderer.
- Solo realiza la validación necesaria en el límite de entrada de usuario y respuesta externa; no repitas la misma validación interna de parámetros entre Renderer, preload, IPC y capas de servicio.

## Datos y tareas en segundo plano

### Ubicaciones de persistencia

| Datos | Ubicación / implementación autoritativa |
|---|---|
| Configuración de usuario y API Keys | `userData/user_config.json`, gestionado por `configStore.cjs` |
| Estado estructurado del negocio | `userData/workspace/savia.sqlite` |
| Markdown fuente importado/analizado, imágenes y productos de tipo archivo | `userData/workspace/<feature>/`, `imported-images/`, `generated-images/` |
| Runtime Pi y tareas persistentes | `userData/agent-runtime/pi/` |
| Registros de diagnóstico de desarrollo | `userData/logs/` |
| Complementos y configuración de complementos | `userData/plugins/`, `userData/plugin-configs/`, `userData/plugin-states.json` |

- Las rutas centrales del espacio de trabajo, configuración, registros y Agent están centralizadas en `electron/utils/paths.cjs`; añade allí primero las nuevas rutas centrales. Las rutas propias de complementos las gestiona actualmente el servicio de complementos.
- Las lecturas/escrituras de archivos del Main usan explícitamente UTF-8, tratando las rutas chinas de Windows como el caso normal.
- La creación de tablas SQLite, las actualizaciones, las comprobaciones de salud y la lógica de respaldo tratan `electron/services/sqliteDatabase.cjs` como la autoridad en ejecución. Al cambiar tablas, añade una migración y sincroniza el esquema objetivo en el `sql/workspace_schema.sql` de la raíz del repositorio.
- Dónde viven los datos (SQLite o sistema de archivos) lo define cada Store: el Markdown fuente importado y las imágenes suelen ser archivos, mientras que el texto del cuerpo de la Propuesta técnica (技术方案) es autoritativo en `technical_plan_outline_nodes.content`. No construyas cachés JSON paralelas según el tamaño del texto; al eliminar recursos de tipo archivo, limpia también su ámbito de imágenes importadas.
- No guardes estado de negocio, borradores ni secretos en el Renderer. El `localStorage` actual solo se usa para el marcador de lectura de anuncios remotos, la hora de publicación de lectura del registro de cambios (`changelog_seen_published_at`), la hora de actualización de lectura de anuncios (`remote_notice_seen_updated_at`) y la migración del id de cliente de analítica heredado al archivo de configuración.

### Single-Section Regeneration

Single-section regeneration on the body-text page reuses the original body-text persistent Session via `contentSectionRegenerationTask.cjs`, reusing the existing `content-generation` task type and entry; it does not delete the Session or workspace. The prompt only provides the target section's current title, number (编号), stable ID, HTML path, and the user's modification request; it does not proactively include other sections' content or reference instructions. The Agent uses Pi native edit and the existing three image tool types (image task files live under `任务/单节修改/`; when replacing an existing image, the corresponding entry sets `regenerate: true`), without re-orchestrating, restoring, checking total word count, performing a consistency audit, or rewriting the full-result manifest; the original audit state is preserved. Only the target body text is modified this time; unrequested images and content stay unchanged, and the original-proposal tables and images remain. The program reads the target HTML, reuses format, image-reference checks, and word counts, then converts only that section's body text according to the Session's template config without inserting outline titles, overwriting the business outline Word file for the same stable ID. Other sections' files and conversion records are untouched; after the target conversion succeeds, clicking the section again previews the latest body text. Runtime reuses `target_item_id`, `regenerate_requirement`, `phase`, and `html_output`; no new tables or fields are added. Pausing/modifying a stage or failing a conversion resumes the original Session (when a modification request was already sent, only send "continue the previous task"; for a new modification round, first clear the previous `prompted_stage`); a conversion-stage failure only retries the conversion. While submitting, running, pausing, or paused, all single-section regeneration entries are disabled, with Main reusing task mutual exclusion. If the Session or target HTML does not exist, report an explicit error; do not auto-rebuild. Run `node scripts/check-content-section-regeneration.cjs --real-word` to check real Pi native editing, Session resumption, mutual exclusion, pause retry, and single-section Word updates.

### Modelo de tareas largas

Cuando "Start generation" en la página del texto del cuerpo (incluidas la generación parcial y la regeneración completa) y la regeneración de una sola sección se ejecutan, el Renderer lee los ajustes de ilustración (配图) guardados en Step02 y el `image_model.status` del canal actual en `user_config.json`, sin iniciar una solicitud de prueba del modelo. En modo imagen con la generación de imágenes por IA habilitada y estado distinto de `available`, se muestra un recordatorio `AppDialog`: cancelar significa no iniciar; continuar significa primero guardar el `contentGenerationOptions.useAiImages` del proyecto actual como false, luego iniciar con la configuración cerrada, y la fase de orquestación ya no programa imágenes de IA. Sin imágenes o con la generación de imágenes por IA desactivada, no se realiza ninguna comprobación; la reanudación tras pausa y el reintento tras fallo reutilizan la configuración guardada sin volver a comprobar, y el Main no añade ninguna interceptación adicional de inicio.

La generación del texto del cuerpo ha eliminado "ignore failed sections and continue": ya no hay botón de ignorar, diálogo de confirmación ni solicitud al backend; el estado de sección `ignored`, el estado de espera de selección del usuario y el campo de recuento de ignorados ya no se usan. Solo `success` marca una sección completada; las secciones fallidas y sin terminar no se excluyen del alcance de generación ni de las estadísticas de recuento de palabras. La generación del texto del cuerpo, las ediciones de una sola sección, las auditorías de coherencia y los fallos de eliminación de tablas reutilizan el reintento de la Session original existente; los fallos de conversión Word solo reintentan la conversión; la exportación del libro completo sigue leyendo todos los HTML de secciones de IA según el esquema actual. Este cambio solo elimina la funcionalidad y su seguimiento de clics; el resto del seguimiento y las estadísticas históricas del servidor se conservan, sin migrar, limpiar ni restablecer datos históricos.

La primera generación del texto del cuerpo, la generación de nuevas secciones y la regeneración completa preparan uniformemente la ejecución antes de la primera persistencia de la tarea: se limpian los objetivos de una sola sección de la ronda anterior, los requisitos de modificación y las etapas de ejecución, comenzando desde la etapa de orquestación. La generación de nuevas secciones conserva los estados de sección, recuentos de palabras y registros Word existentes; la regeneración completa elimina la Session anterior del texto del cuerpo según las reglas antiguas, y limpia el texto del cuerpo anterior, la orquestación, los recuentos de palabras y los registros de conversión en la primera persistencia, reconstruyendo el estado pendiente. La reanudación y el reintento tras fallo conservan la ejecución y la Session actuales sin nueva inicialización de tarea; incluso si la aplicación se cierra tras la primera persistencia pero antes del primer punto de control del ejecutor, el reinicio se reanuda como la misma ronda de tarea. Las comprobaciones de recuperación al inicio están incluidas en `node scripts/check-outline-content-state.cjs` y `node scripts/check-content-generation-output.cjs`.

When resuming a half-finished body-text task, only send "continue the previous task" (`CONTINUE_PROMPT` in `contentGenerationAgent.cjs`); the Agent continues based on the original Session history and workspace without resending the full stage requirements. The criterion is the `prompted_stage` written by the Pi Runtime into the persistent task state before each stage prompt is sent to the Session (`wasStagePrompted()`): on pause-resume or failure retry, if the current stage (planning, generation, audit, table removal, format补写/supplementary writing, original-proposal restoration, single-section modification, export repair) requirement was already sent, only send the continue phrase; if not yet sent (e.g. pausing during audit review or handoff compaction), still send the full stage requirement; if audit or table removal is already done, follow the program's short closing prompt. A new task round (partial generation, full regeneration) and a new single-section modification first clear `prompted_stage` and `compaction_pending` to null to avoid misjudging as resume. When the Agent does not finish the current stage before ending the round in the same run (audit without submitting conclusions, table removal unfinished, format补写/supplementary writing unsubmitted), likewise only send the continue phrase; execution failures (model or service interruption) auto-retry with the continue phrase, submission-validation failures still return the full problem list, and basic-orchestration execution failures still do not auto-retry. Old Sessions from before this change have no such record; their first resume still sends the full requirement. The page retry log describes real progress: for the generation stage, write "kept N sections with existing non-empty HTML, no regeneration; this run fills M sections" based on the last scanned non-empty HTML, and for audit, table removal, and format self-check resumes write "resuming from the {stage name} stage", no longer showing "retrying N failed or unfinished body sections". Coverage is provided by `piRuntimeService.test.cjs`, `check-content-generation-agent.cjs`, `check-content-generation-output.cjs`, and `check-content-section-regeneration.cjs`.

`taskService.cjs` gestiona uniformemente las tareas de Propuesta técnica (技术方案), Verificación de duplicados de oferta (标书查重), Verificación de descalificación (废标检查) y Verificación de cumplimiento ciego (暗标合规检查); cada grupo de negocio es actualmente mutuamente excluyente dentro de su grupo. La base de conocimiento es una excepción explícita: `knowledgeBaseService.cjs` mantiene el conjunto de actividades de preparación/coincidencia por documento y lo envía vía `knowledge-base:event`. La exportación Word tiene sus propios eventos de progreso independientes.

La búsqueda global de la base de conocimiento usa `knowledgeBase.search({ keyword, page })`, con páginas que empiezan en 1 y devuelven `{ items, total, page, pageSize }` con 100 elementos por página. El `total` y la página actual se consultan en la misma transacción de lectura SQLite; cuando la reducción de datos deja el número de página fuera de rango, se devuelve la última página válida. El Renderer muestra usando el número de página y el total devueltos, conserva la palabra clave enviada al cambiar de página, conserva la última página exitosa en caso de fallo y deja que una solicitud sin terminar caduque cuando se limpia la búsqueda. La recuperación sigue siendo exploración sincrónica de subcadenas en el Main; la paginación no implica indexación de texto completo ni consultas en hilos de segundo plano.

Las tareas gestionadas siguen este flujo:

1. El Main crea una tarea en ejecución y persiste el estado inicial.
2. El progreso de alta frecuencia sin valor de recuperación llama a `updateTask()`, actualizando solo la memoria del Main y enviando eventos.
3. Los resultados de etapa llaman a `checkpointTask(taskPatch, workspacePatch, eventPatch)`, confirmando la tarea y el parche de negocio en una transacción del Store, y luego enviando el mismo evento parcial tras el éxito.
4. Cerrar la página no cancela las tareas; volver a montar restaura la vista desde el Store y la reproducción de tareas activas.
5. La política de recuperación tras reinicio la decide `taskService.cjs` por tipo de tarea: las tareas de texto del cuerpo pueden quedar pausadas, el esquema en espera de selección solo se reanuda cuando la Session persistente está intacta, y otras tareas interrumpidas suelen quedar en error. El Renderer no convierte por sí solo un estado en ejecución restante en inactivo.

Los comandos del Main que limpian tareas o resultados derivados primero deben cancelar las tareas activas relevantes, esperar a que el ejecutor se asiente y luego confirmar el Store; un ejecutor cancelado no debe seguir confirmando. La importación, eliminación y restablecimiento de Propuesta técnica (技术方案) y Verificación de descalificación (废标检查) ya pasan por la cadena `beforeCommit` de `taskService`; las nuevas entradas deben reutilizar ese patrón.

### Verificación de cumplimiento ciego (暗标合规检查)

"Bid Check (标书检查) → Blind Compliance Check (暗标合规检查)" (`features/blind-check/`) tiene cuatro pasos: seleccionar el documento de oferta, requisitos de formato, resultados de verificación y corrección automática. La arquitectura es prefiltrado por programa + revisión por IA: las verificaciones del programa son la acción `blind-check-inspect` de OpenXmlHelper, que solo maneja reglas con parámetros explícitos, conclusiones deterministas y comportamiento modificable con precisión; todo lo que requiera leer y comprender la licitación (招标文件) o el contenido de la oferta se deja a un Agent persistente (ver «Revisión por IA» más abajo). El protocolo, las reglas y la semántica de evaluación están documentados en `openxmlhelper/开发说明.md`. En el lado del Main se compone de `blindCheckStore.cjs` (tablas SQLite `blind_check_*`), `blindCheckPresets.cjs`, `blindCheckTask.cjs`, `blindCheckFixTask.cjs`, `blindCheckAgent.cjs`, `blindCheckReview.cjs` y el IPC ligero `blindCheckIpc.cjs`, con los tipos de tarea `blind-check-run` y `blind-check-fix`.

- Solo se acepta `.docx`. Al importar, el archivo se copia a `workspace/blind-check/source/<UUID>.docx`; las verificaciones solo se ejecutan contra la copia. Cambiar de archivo o eliminar un archivo primero cancela las verificaciones y correcciones en curso y espera a que el proceso ayudante termine antes de confirmar; extraer presets del documento de licitación es independiente del documento bajo verificación y no se cancela al cambiar de archivo — solo el restablecimiento cancela todo el grupo.
- Los presets integrados se definen en `blindCheckPresets.cjs` y son de solo lectura; los presets regionales están marcados como valores de referencia. Los usuarios deben usar "Copy as my preset" antes de editar; los presets de usuario se guardan en `blind_check_presets`. Los campos de preset solo reconocen lo que el motor usa realmente; la entrada del usuario se normaliza una vez en `normalizeProfile()`, los campos desconocidos se descartan y null significa que ese elemento no se verifica (la licitación no lo exige). Los efectos del texto del cuerpo (`body.allow_*`), el contenido de encabezado/pie, los párrafos vacíos y el tamaño de papel pueden ser todos null; la interfaz es una elección triple de "tender does not require / disallow / allow". La negrita de tabla `table.allow_bold` con null significa igual que el texto del cuerpo; la cursiva, el color y otros efectos de tabla siempre siguen al texto del cuerpo.
- La información empresarial de credenciales de la biblioteca de calificación (nombre de empresa y su nombre corto sin sufijo, código de crédito, representante legal, teléfono, correo, dirección, nombre de cuenta, cuenta bancaria) la lee el Main al iniciar la verificación y la pasa al motor como palabras sensibles; el interruptor se guarda en `blind_check_meta.use_credential_words` y no se guarda con los presets. Los nombres de personas no se incluyen.
- La firma de entrada se compone del hash del contenido del documento, el ID de preset, el preset normalizado y las palabras sensibles (un ID de preset representa la base de licitación: el texto fuente de la licitación y la procedencia contrastada se guardan con el preset; dos presets con idéntica configuración de formato pero distinto ID se tratan como entradas diferentes), calculada por el Main (`getInputSignature`). Las verificaciones no inician automáticamente: en la página "Check results" haz clic en "Start check" ("Re-check" cuando ya existen resultados) y elige en el diálogo entre solo verificación por programa o verificación por programa + revisión por IA; la elección se pasa con `tasks.startBlindCheck({ aiReview })`. Cuando la firma difiere del resultado existente, la página muestra que el resultado ha caducado. El progreso solo se envía, no se persiste; la finalización escribe los resultados fusionados y el estado de la tarea en un punto de control. Al reiniciar la aplicación, las tareas en ejecución restantes se marcan como fallidas.

## Invariantes clave de la Propuesta técnica (技术方案)

La auditoría de cobertura de la propuesta original, la orquestación heredada de imágenes de texto completo y los flujos de ilustración de seguimiento se han eliminado, incluidas la entrada de reilustración, el progreso dedicado, el almacenamiento de planes y elementos de imagen; se mantienen la restauración de la propuesta original, las tablas e imágenes conservadas durante la generación, las nuevas herramientas de ilustración del Agent y la protección de imágenes. La Auditoría de coherencia (一致性审计) y la Eliminación de tablas (去表格) se completan en la Session principal persistente del texto del cuerpo. Las bases de datos nuevas ya no crean tablas heredadas de planes/proyectos de ilustración ni las tres columnas de tope de imágenes, y la reparación al inicio no exige que existan; las tablas, columnas y datos existentes no se migran ni se eliminan de forma proactiva, y los números históricos de migración permanecen sin cambios.

El "Reset" de flujo completo primero reutiliza `taskService` para cancelar tareas en segundo plano, esperar a que terminen y cerrar OpenXmlHelper; luego el Store elimina `workspace/technical-plan/` por completo más las imágenes generadas exclusivas del flujo, las imágenes importadas y las Sessions persistentes del Agent, limpia los registros de flujo por tabla de negocio y restaura la configuración inicial. Esta entrada no prepara ni elimina archivos Word por ID de sección; los archivos Word no registrados, los archivos preparados y las plantillas de oferta extraídas se limpian con el directorio exclusivo. Los archivos fuente subidos por el usuario, la base de conocimiento compartida, la biblioteca pública de plantillas, la configuración global y otros datos de negocio no se limpian. El restablecimiento de etapa del texto del cuerpo, el guardado de hechos globales y las modificaciones del esquema siguen sus alcances originales de invalidación parcial. El Renderer relee el estado completo y reemplaza la instantánea de la página en `finally` para el restablecimiento de flujo completo, el restablecimiento de etapa del texto del cuerpo, el guardado de hechos globales y el guardado del esquema; el contexto de vista previa Word se actualiza incluso si la operación falla. El error original de la operación sigue mostrándose; los fallos de actualización se explican por separado y nunca se informan como un restablecimiento exitoso.

La Propuesta técnica (技术方案) usa uniformemente la entrada `technical-plan`; Step02 permite opcionalmente subir una propuesta existente, y las etapas de esquema, Hechos globales (全局事实) y texto del cuerpo deciden si habilitan la expansión de propuesta original según exista `originalPlanFile`, sin mantener una entrada de expansión separada ni un interruptor de flujo.

Project-level generation config is uniformly saved in `technical_plan_generation_config`, `technical_plan_generation_bid_tasks`, and `technical_plan_generation_reference_docs`; Main reads/writes it via `technicalPlanStore.loadGenerationConfig()` / `saveGenerationConfig()`, and Renderer uses the same-named `window.savia.technicalPlan` API. Step02 "What it looks like (长嘛样)" defaults to the system template "Standard Bid - Simplified (标准投标简版)" (`tpl-system-standard-bid`) after config initialization or full-flow reset, without auto-rewriting existing config. Step02 "What to write (写嘛)" reuses `outlineMode`: `response-file`, `standalone-technical`, and `standalone-business` mean full bid document, standalone technical volume, and standalone commercial volume respectively; after config initialization or full-flow reset the default is standalone technical volume. Full bid document and standalone commercial volume are not yet developed; the page locks them as unselectable, showing only the shared `githubStarNotice` in-development hint on click, while the Main outline-generation chain still keeps all three values without rewriting existing config. "I have a proposal (我有方案)" saves `outlineExpansionMode`, "Knowledge base (知识库)" saves `referenceKnowledgeDocumentIds`, "How much to write (写多少)" saves `outlineWordControlOptions` and `contentGenerationOptions.tableRequirement`, "Illustrations (插图吗)" saves the illustration ratio, four illustration-layout switches, and AI, Mermaid, and HTML illustration fields, and "How to write (怎么写)" saves `globalFactsMode`. Selections, switches, and dropdowns save immediately on change; numeric or text inputs save on blur or Enter; each success shows "Saved successfully (保存成功)". The outline-generation, global-facts, and body-text pages no longer maintain these generation settings; clicking generate or regenerate directly uses the Step02 saved config. Consistency Audit (一致性审计) completes inside the body-text persistent main Session; when "No tables (不要表格)" is selected, data tables are converted to plain text in the same Session after the audit, then converted to Word. The body-text page no longer provides a config dialog. In developer mode, the body-text operation area provides "Reset body-text stage (重置正文阶段)". Modifying generation config before a body-text task starts only updates storage without clearing existing results; once a body-text task starts (including orchestration and restoration stages), everything in Step02 is locked except the export template and template style scope under "What it looks like (长嘛样)" ("Format self-check and repair (格式自检及修复)" under the same tab is likewise locked). The lock persists across pause, failure, completion, and restart; outline add/delete/modify does not unlock. Explicitly resetting body text or confirming global-facts modification with body-text clearing unlocks it. Lock state reuses the body-text runtime save; no separate config table is created. Models, APIs, file parsers, and Word export styles remain global `user_config.json`; the outline word-count effective snapshot, task runtime, and business results are not editable generation config.

El orden y los nombres de las pestañas de Step02 están centralizados en `generationSettingsTabs.ts`; la pestaña actual la controla `TechnicalPlanHome`: entrar a Step02 cae por defecto en el primer elemento, volver desde Step03 cae en el último elemento, y la entrada "Go to what-it-looks-like (去长嘛样)" de la página del texto del cuerpo salta directamente a "What it looks like (长嘛样)". La segunda fila de pestañas muestra un resumen "palabra-de-función · valor-actual (功能词·当前值)", leyendo solo la configuración guardada, nunca el borrador en curso; los estilos relacionados están limitados bajo `.generation-settings-page` y no afectan a las páginas de biblioteca de calificación y ajustes de plantilla que reutilizan las mismas clases de pestaña.

Basic planning, body-text generation, optional word-count correction, Consistency Audit (一致性审计), optional table removal, and format supplementary writing use one main `agentService.runTask()`, continuously executed in the same running Pi Session via the existing `continueTask`, with task id `technical-plan-content-generation`. Normal continuous execution creates only one main Runtime/Session; do not substitute multiple openings of the same persistent Session for stage resumption. The internal `planning` stage and progress range are kept: the main Agent first submits basic planning, the program validates, corrects target word counts, selects tables and illustrations, and saves, then resumes generation in the same Session. Original-proposal restoration still uses a separate task, executed between the two as needed. The basic planning's `正文编排目录.json` (body-planning outline JSON) is read-only reference containing the full outline and existing planning; current-round target IDs are written to the read-only `正文编排目标.json` (body-planning targets JSON), with prompts giving only counts. A new planning round clears results; resuming in the planning stage after pause or failure in the same round keeps drafts. Input references refresh with the current outline. Old full-outline results are not accepted; no compatibility parsing or data migration is added. Saved planning data structures and versions are unchanged. Los Agents no deben terminar tareas por sí mismos: `report-failure` es cambiado uniformemente por `pi/piTaskFailureTool.cjs` a una solicitud de terminación; la herramienta primero muestra el motivo al usuario a través del canal de preguntas del runtime, recordando que continuar requiere bajar la calidad, con opciones fijas "Continue with lower quality", "Terminate task", "Add handling requirements" (entrada personalizada). Solo tras confirmar el usuario la terminación, la tarea termina con el existente `AGENT_REPORTED_FAILURE`, añadiendo "(terminated per your choice)" (已按您的选择终止任务) al mensaje de error, contando igualmente en estadísticas y diagnósticos de fallos del Agent. Al elegir continuar o añadir requisitos, la herramienta devuelve instrucciones relajadas al Agent: todos los requisitos de calidad pueden bajarse o abandonarse; el único mínimo es escribir los archivos requeridos, pasar la validación del programa y mantener el flujo continuando establemente, con prioridad para los requisitos añadidos por el usuario. La primera confirmación en la misma ejecución permite respuesta automática (autoselección de continuar); tras elegir continuar, volver a solicitar la terminación desactiva la respuesta automática (`auto_answer=false`), exigiendo elección manual. Las respuestas de confirmación de terminación no se escriben en `user_question_answers` legibles por el negocio, solo registran actividad visible. Las reglas surten efecto en la capa de herramientas para todos los Agents y todas las etapas, independientemente de si la etapa abre `ask-user`; el "call report-failure" en prompts de negocio no necesita reescritura. Las sub-Sessions con `failure_handled_by_parent=true` y las Sessions sin canales de preguntas (autoverificación del entorno de ejecución) siguen informando fallos directamente. La terminación del lado del programa tras bloqueo continuo de validación de envío no está en esta regla.

Submission validation: file writes are not validated or intercepted at the write/edit layer; `json_validation_schemas` is only for Agent self-check. After the Agent ends a round, Runtime first restores protected files, then `validateOutput` returns a unified report `{ value, issues, progress?, minimumGoal? }`: each `issues` item uses `severity=blocking|quality` and `message` to describe problems, keeping other business positioning fields. Return an empty array when there are no problems. Errors affecting JSON reading, product integrity, HTML conversion, or necessary images are blocking; word counts, consistency, residual tables, and unfinished format补写/supplementary-writing are quality. Business validation normally returns reports; file reading, model interruption, and program exceptions still throw and follow `max_retries` without consuming submission-repair budgets. `pi/piSubmissionPolicy.cjs` uniformly maintains adjacent-two-round progress per stage: blocking-problem count first; when both are zero, compare quality-problem count or program-provided numeric remainder (word-count difference). One round without improvement requires changing methods; after two consecutive rounds without improvement, record-then-accept when only quality problems remain, or lower quality constraints with an explicit minimum goal and try one last round when blocking problems exist, terminating only when still blocked. The fixed three-attempt total cap is removed; continue repairing on improvement, without resetting on same-stage continuation, rebuilding policy only when truly switching stages or rerunning after pause. The public layer splices repair-mode notes; business callbacks only supplement file and tool information. On acceptance, `report.value` is passed as `validation_result` to out-of-loop `continueTask`, with放行/waived problems in `accepted_issues`. Final results keep `accepted_submission_issues` without disguising quality leftovers as repair success. Protected files are still managed by `pi/piWorkspaceBaseline.cjs`; registered inputs, non-target sections, original images, and ledgers are restored before submission with activity recorded, keeping image-block comparison. Body-text main stages reuse one manifest and section read, plus current-stage quality rules. Audit, table removal, and format补写/supplementary-writing completion tools only save submission requests; the main flow advances state only after acceptance. Shared edit subtasks check products once on exit and return problems and facts; repair decisions belong to main stages. Standalone single-section modification still has its own main-task submission policy. Submission problems spanning more than five sections continue using `fix-submission-issues`; others are directly modified by the main Agent. Outline, Global Facts (全局事实), body-text planning, original-proposal restoration, and template extraction all use the same report protocol, incompatible with old return structures. Checks reuse `node --test electron/services/pi/piRuntimeService.test.cjs` and `node scripts/check-content-generation-agent.cjs`.

- Las nuevas importaciones de documentos prefieren reutilizar `fileService.cjs` / `parseDocumentWithConfig()`, manteniendo la elección local-o-MinerU de la configuración, el repliegue de formato, el ámbito de imágenes y la copia de error unificada. Para avisos de LibreOffice faltante, reutiliza `DocumentParseNoticeProvider`.
- La exportación Word pasa uniformemente por `exportService.cjs` y `window.savia.export.onWordExportProgress()`; la conversión de imágenes Mermaid/HTML la completa localmente el Main.
- Las imágenes generadas son comprimidas por `electron/utils/imageCompression.cjs` antes de aterrizar: imágenes generadas por IA en el `saveGeneratedImage()` de `aiService.cjs`, renderizados HTML/Mermaid del texto del cuerpo en el `renderImage()` de `contentGenerationImageTools.cjs`. Las imágenes que superen 1920×2880 se reducen proporcionalmente, las áreas transparentes se aplanan a blanco, convertidas uniformemente a JPEG (calidad 90). Las imágenes GIF o indecodificables se guardan tal cual. Las referencias posteriores del texto del cuerpo, vistas previas, exportación Word y autoverificación de formato usan directamente archivos comprimidos; las imágenes históricas no se migran.
- Las modificaciones parciales de texto devueltas por la IA reutilizan `electron/utils/textEdit.cjs`: usa `applyTextEdit()` / `applyTextEdits()` con aciertos únicos para posiciones desconocidas, `applyRangeEdit()` / `applyRangeEdits()` para rangos conocidos. Los casos sin coincidencia o con múltiples coincidencias deben devolver errores; no añadas silenciosamente el contenido de reemplazo al final.
- Caché de prefijo de prompt: los servicios de modelo solo escriben caché al final del último mensaje de una solicitud; las solicitudes posteriores solo aciertan cuando los prefijos coinciden textualmente en límites de mensaje. Los prefijos idénticos dentro del mismo mensaje, las divisiones de bloques de contenido, `cache_control` y `prompt_cache_key` no tienen efecto. Los materiales compartidos entre solicitudes van como mensajes independientes antes del contenido cambiante; las reglas fijas no se colocan tras el contenido cambiante. Al emitir dos o más solicitudes concurrentes o consecutivas, usa primero `warmPromptPrefix()` en `electron/utils/promptPrefixCache.cjs` para enviar una solicitud de calentamiento solo de prefijo (tope de salida 1; los fallos no afectan a solicitudes posteriores), construyendo prefijos con la misma función para calentamiento y solicitudes formales. El procesamiento por lotes del texto del cuerpo (`sharedPrefixMessages()`), el análisis de licitación (por segmento de licitación), el texto del cuerpo y la revisión del estudio de viabilidad, los prefijos de bloque L1 de la base de conocimiento y las entradas multilote, y los mensajes compartidos de fuente de licitación para verificaciones de descalificación/tipografía/lógica están todos organizados así.
- Al solucionar anomalías, primero registra la etapa reproducible, el resumen de entrada y la cadena de errores: los registros de módulo en modo desarrollador usan `createDeveloperLogger()` para escribir en `userData/logs/<module>/`; los registros de solicitudes de IA están en `userData/logs/ai/`. Los registros de archivo descartables se escriben asíncronamente vía `silentFileLog.cjs`; los fallos de registro no deben afectar al flujo principal.

## Código relacionado a nivel de repositorio

`client/` no depende de otros directorios heredados frontend/backend del repositorio. Solo el siguiente código a nivel de repositorio necesita verificaciones de enlace cuando cambia:

| Directorio | Cuándo revisar |
|---|---|
| `analytics/worker/` | Al modificar protocolos de subida de eventos, campos, estadísticas de modelos, estadísticas de ejecución del Agent o diagnóstico de fallos |
| `analytics/dashboard/` | Al añadir rutas de página, configurar dimensiones de estadísticas o ajustar la visualización del Dashboard |
| `sql/workspace_schema.sql` | Al modificar migraciones de `sqliteDatabase.cjs` o estructuras de tablas objetivo; la ejecución sigue las migraciones |
| `.github/workflows/release.yml`, `.github/scripts/` | Al modificar objetivos de empaquetado, nombrado de artefactos, atestaciones de compilación, manifiestos de actualización o canales de publicación |
| `openxmlhelper/` | Al modificar protocolos del ayudante Word / Open XML, convenciones de directorios de tarea o empaquetado en extraResources; ver `openxmlhelper/开发说明.md` para detalles |

La entrada de seguimiento del Renderer es `src/shared/analytics/analytics.ts`; las estadísticas de IA y Agent están en el `aiService.cjs` del Main y en `services/agent/` respectivamente. Los fallos de seguimiento deben ser silenciosos sin afectar al flujo principal; las estadísticas existentes nunca deben eliminarse ni omitirse. El seguimiento ordinario `/track` no debe subir API Keys, Prompts, respuestas de modelo, contenidos de archivo, nombres de archivo ni rutas locales. El diagnóstico de fallo final del Agent es una cadena independiente `/agent-errors`, recopilada por un proceso dedicado con un paquete de diagnóstico desensibilizado; no debe fusionarse en el seguimiento ordinario ni debilitarse arbitrariamente. Al añadir nuevas páginas de menú, completa el mapeo de nombres chinos del Dashboard antes mencionado.
