# Savia Bidding Toolbox Development Guide (Savia Licitaciones开发说明)

This document is for members working on `client/`. Feature behavior is defined by the current code; this document only keeps the stable rules that help you locate code, collaborate across processes, reuse UI, maintain persistent state, and complete verification.

## Quick Start

There is no client `package.json` at the repository root. Run all client commands from inside `client/`:

```powershell
cd client
npm ci             # Install dependencies; postinstall rebuilds native modules for the current Electron
npm run dev        # Start Vite at 127.0.0.1:5173, then open Electron
npm run build      # tsc --noEmit && vite build
```

- CI uses Node 22. When local and release builds differ, align to that version first.
- `better-sqlite3` is an Electron native dependency. If you see a `NODE_MODULE_VERSION` mismatch, run `npm run postinstall`; verify the ABI with `npm run smoke:electron-native` instead of loading a Store in a plain Node process.
- The project has no unified lint script and no project-wide test script; run existing `*.test.cjs` files individually with `node --test <file>` according to the scope of your change.

## Runtime Structure

```text
src/main.tsx
├─ Standalone developer window (selected by ?window=...)
└─ AppProviders
   └─ WorkspaceDatabaseGate
      └─ App
         └─ AppShell + AppRouter

Renderer
  └─ window.savia
      └─ electron/preload.cjs
          └─ electron/ipc/*.cjs
              └─ electron/services/*.cjs
                  ├─ SQLite Store / config
                  ├─ Files and export
                  └─ AI / Agent / background tasks
```

- Renderer is Vite + React + TypeScript ESM; Electron Main, preload, IPC, and Main services are CommonJS, keeping the `.cjs` extension.
- The main window enables `contextIsolation` and disables `nodeIntegration`. Renderer does not import `electron`, `fs`, or `path`, nor does it use `ipcRenderer` directly; local capabilities are uniformly exposed through `window.savia`.
- Renderer is responsible for page state and interaction orchestration; Main is responsible for config, SQLite, file parsing, AI, Agent, background tasks, export, plugins, and updates.
- `WorkspaceDatabaseGate` blocks business pages from mounting until database checks, migrations, and history cleanup are done; database-related IPC is also pre-registered as pending/unavailable handlers.
- `AppRouter` is component dispatch based on `SectionId`, not URL routing. Do not add pages following React Router conventions.

| Location | Responsibility |
|---|---|

| `src/components/` | App shell components, currently mainly `AppShell`, `Sidebar` |
| `src/features/<feature>/` | Feature pages and their dedicated components, Hooks, types, and lightweight Renderer orchestration; create directories according to actual complexity, do not add empty layers |
| `src/shared/ui/` | Cross-feature UI components and global interaction Providers |
| `src/shared/types/` | Cross-feature types, navigation types, and `window.savia` bridge types |
| `src/shared/prompts/` | Prompt builders still used in Renderer |
| `src/shared/utils/`, `src/shared/markdown/` | Cross-feature pure utilities and Markdown rendering helpers |
| `src/styles/` | Tokens, shell, shared-component, and per-feature styles; `src/styles.css` is the single entry point |
| `electron/main.cjs` | Windows, protocols, app lifecycle, and Main entry |
| `electron/preload.cjs` | Main-window bridge; dragged file paths are also exposed here via `webUtils`; the plugin-config window uses a separate `preload-plugin-config.cjs` |
| `electron/ipc/` | IPC registration and parameter forwarding; `index.cjs` handles service assembly and database lifecycle |
| `electron/services/` | Main business services, Stores, and task implementations; `agent/`, `pi/`, `doc2markdown/` are dedicated sublayers |
| `electron/utils/` | Main pure utilities, paths, logging, queues, text editing, and imported-image cleanup |
| `electron/resources/` | Agent instructions, public license keys, and build attestations packaged into the client |
| `vendor/agent-tools/`, `scripts/` | Bundled Agent command tools and build/verification scripts |

Placement principles:

- Code used by only one feature stays in that feature; only move it up to `shared/` after real cross-feature reuse appears.
- Runtime code in `shared/` must not depend on features. The existing `shared/types/ipc.ts` and `shared/types/index.ts` combine or re-export some feature types; this is the existing bridge/type boundary and should not be extended into shared code referencing feature components or services.
- Renderer `services/` only performs bridge calls or lightweight orchestration; time-consuming flows and authoritative persistence live in Main.
- New business IPC stays thin by default. The lifecycle assembly in `ipc/index.cjs` and the existing plugin-market/config orchestration in `pluginIpc.cjs` are exceptions; do not copy them as templates for ordinary features.
- Do not write Prompts inside components: Renderer Prompts go in `src/shared/prompts/`; Main background-task Prompts live with their task services.

### Adding a New Menu Page

Check at least the following locations:

1. `src/shared/types/navigation.ts`: add a `SectionId`.
2. `src/app/menuConfig.ts`: configure the first- or second-level menu.
3. `src/app/AppRouter.tsx`: register the page dispatch.
4. `src/components/Sidebar.tsx`: add the icon mapping for `navigationIcons`.
5. `analytics/dashboard/public/src/pages/traffic.js`: add the Chinese display name for the new tracking route.

When a first-level menu has `children`, `AppRouter` uses `shared/ui/SecondaryMenuPage.tsx` to show the second-level entry; do not implement expandable menus in the sidebar. The settings page is a separate entry at the bottom of the sidebar.

## Renderer and Main Collaboration

When adding or modifying a bridge API, update the full chain:

1. Implement the capability or Store operation in `electron/services/`.
2. Register the channel in the corresponding `electron/ipc/*Ipc.cjs` and wire dependencies in `electron/ipc/index.cjs`.
3. If the channel depends on the workspace database, also add it to `workspaceDatabaseChannels` in `index.cjs` so it is neither missed nor double-registered before the database is ready.
4. Expose the method or event in `electron/preload.cjs`.
5. Synchronize parameter, return-value, and event types in `src/shared/types/ipc.ts`; the global declaration references that type from `src/vite-env.d.ts`.

Other conventions:

- `onXxx` event APIs must return an unsubscribe function; call it when the React effect unmounts.
- Managed task pages first read the Store snapshot, then subscribe to `tasks.onTaskEvent()`, then call `tasks.getActiveTasks()`; the last step subscribes again and replays active tasks, avoiding the case where the first event fires before the listener is registered.
- IPC patch semantics are "field presence": a missing field means keep, a present field means apply that value; `undefined`, `null`, or empty collections are usually used for explicit cleanup, as defined by each Store. When merging patches in Renderer, use `hasOwnProperty`; do not use truthiness checks.
- Command interfaces may return `void`, an entity, or a partial patch; do not assume every write returns the full workspace. Call `load*` / `get*` / `list*` explicitly when full state is needed.
- A browser `File` obtained by drag-and-drop is converted to a local path via `window.savia.file.getPathForFile(file)`; do not read the non-standard `file.path`.
- External links go through `window.savia.openExternal()`; locally imported images and generated images use the Main-registered `savia-asset://imported-images/...` and `savia-asset://generated-images/...`. Do not expose `file://` paths to Renderer.
- Only perform necessary validation at the user-input and external-response boundary; do not repeat the same internal parameter validation across Renderer, preload, IPC, and service layers.

## Data and Background Tasks

### Persistence Locations

| Data | Location / authoritative implementation |
|---|---|
| User config and API Keys | `userData/user_config.json`, managed by `configStore.cjs` |
| Structured business state | `userData/workspace/savia.sqlite` |
| Imported/parsed source Markdown, images, and file-type products | `userData/workspace/<feature>/`, `imported-images/`, `generated-images/` |
| Pi runtime and persistent tasks | `userData/agent-runtime/pi/` |
| Development diagnostic logs | `userData/logs/` |
| Plugins and plugin config | `userData/plugins/`, `userData/plugin-configs/`, `userData/plugin-states.json` |

- Core workspace, config, log, and Agent paths are centralized in `electron/utils/paths.cjs`; add new core paths there first. Plugin-owned paths are currently managed by the plugin service.
- Main file reads/writes explicitly use UTF-8, treating Windows Chinese paths as the normal case.
- SQLite table creation, upgrades, health checks, and backup logic treat `electron/services/sqliteDatabase.cjs` as the runtime authority. When changing tables, add a migration and synchronize the target schema in the repository-root `sql/workspace_schema.sql`.
- Whether data lives in SQLite or the file system is defined by each Store: imported source Markdown and images are usually files, while Technical Proposal (技术方案) body text is authoritative in `technical_plan_outline_nodes.content`. Do not build parallel JSON caches based on text size; when deleting file-type resources, also clean up their imported-image scope.
- Do not save business state, drafts, or secrets in Renderer. Current `localStorage` is only used for the remote-announcement read marker, the changelog read publish time (`changelog_seen_published_at`), the announcement read update time (`remote_notice_seen_updated_at`), and migration of the legacy analytics client id to the config file.

### Single-Section Regeneration

Single-section regeneration on the body-text page reuses the original body-text persistent Session via `contentSectionRegenerationTask.cjs`, reusing the existing `content-generation` task type and entry; it does not delete the Session or workspace. The prompt only provides the target section's current title, number (编号), stable ID, HTML path, and the user's modification request; it does not proactively include other sections' content or reference instructions. The Agent uses Pi native edit and the existing three image tool types (image task files live under `任务/单节修改/`; when replacing an existing image, the corresponding entry sets `regenerate: true`), without re-orchestrating, restoring, checking total word count, performing a consistency audit, or rewriting the full-result manifest; the original audit state is preserved. Only the target body text is modified this time; unrequested images and content stay unchanged, and the original-proposal tables and images remain. The program reads the target HTML, reuses format, image-reference checks, and word counts, then converts only that section's body text according to the Session's template config without inserting outline titles, overwriting the business outline Word file for the same stable ID. Other sections' files and conversion records are untouched; after the target conversion succeeds, clicking the section again previews the latest body text. Runtime reuses `target_item_id`, `regenerate_requirement`, `phase`, and `html_output`; no new tables or fields are added. Pausing/modifying a stage or failing a conversion resumes the original Session (when a modification request was already sent, only send "continue the previous task"; for a new modification round, first clear the previous `prompted_stage`); a conversion-stage failure only retries the conversion. While submitting, running, pausing, or paused, all single-section regeneration entries are disabled, with Main reusing task mutual exclusion. If the Session or target HTML does not exist, report an explicit error; do not auto-rebuild. Run `node scripts/check-content-section-regeneration.cjs --real-word` to check real Pi native editing, Session resumption, mutual exclusion, pause retry, and single-section Word updates.

### Long-Task Model

When "Start generation" on the body-text page (including partial generation and full regeneration) and single-section regeneration run, Renderer reads the illustration (配图) settings saved in Step02 and the current channel's `image_model.status` in `user_config.json`, without initiating a model test request. In image mode with AI image generation enabled and status not `available`, show an `AppDialog` reminder: cancel means do not start; continue means first save the current project's `contentGenerationOptions.useAiImages` as false, then start with the closed config, and the orchestration phase no longer schedules AI images. With no images or AI image generation off, no check is performed; pause-resume and failure retry reuse the saved config without re-checking, and Main adds no extra startup interception.

Body-text generation has removed "ignore failed sections and continue": there is no longer an ignore button, confirmation dialog, or backend request; the `ignored` section state, waiting-for-user-selection state, and ignored-count field are no longer used. Only `success` marks a completed section; failed and unfinished sections are not excluded from the generation scope or word-count statistics. Body-text generation, single-section edits, consistency audits, and table-removal failures all reuse the existing original-Session retry; Word conversion failures only retry conversion; full-book export still reads all AI section HTMLs according to the current outline. This change only removes the feature and its click tracking; other tracking and historical server-side statistics are retained, without migrating, cleaning, or resetting historical data.

First body-text generation, new-section generation, and full regeneration uniformly prepare runtime before the first task persistence: clear the previous round's single-section targets, modification requirements, and execution stages, starting from the orchestration stage. New-section generation keeps existing section states, word counts, and Word registrations; full regeneration deletes the old body-text Session per the old rules, and clears old body text, orchestration, word counts, and conversion records on first persistence, rebuilding the pending state. Resume and failure retry keep the current runtime and Session without new task initialization; even if the app exits after first persistence but before the runner's first checkpoint, restart resumes as the same task round. Startup recovery checks are included in `node scripts/check-outline-content-state.cjs` and `node scripts/check-content-generation-output.cjs`.

When resuming a half-finished body-text task, only send "continue the previous task" (`CONTINUE_PROMPT` in `contentGenerationAgent.cjs`); the Agent continues based on the original Session history and workspace without resending the full stage requirements. The criterion is the `prompted_stage` written by the Pi Runtime into the persistent task state before each stage prompt is sent to the Session (`wasStagePrompted()`): on pause-resume or failure retry, if the current stage (planning, generation, audit, table removal, format补写/supplementary writing, original-proposal restoration, single-section modification, export repair) requirement was already sent, only send the continue phrase; if not yet sent (e.g. pausing during audit review or handoff compaction), still send the full stage requirement; if audit or table removal is already done, follow the program's short closing prompt. A new task round (partial generation, full regeneration) and a new single-section modification first clear `prompted_stage` and `compaction_pending` to null to avoid misjudging as resume. When the Agent does not finish the current stage before ending the round in the same run (audit without submitting conclusions, table removal unfinished, format补写/supplementary writing unsubmitted), likewise only send the continue phrase; execution failures (model or service interruption) auto-retry with the continue phrase, submission-validation failures still return the full problem list, and basic-orchestration execution failures still do not auto-retry. Old Sessions from before this change have no such record; their first resume still sends the full requirement. The page retry log describes real progress: for the generation stage, write "kept N sections with existing non-empty HTML, no regeneration; this run fills M sections" based on the last scanned non-empty HTML, and for audit, table removal, and format self-check resumes write "resuming from the {stage name} stage", no longer showing "retrying N failed or unfinished body sections". Coverage is provided by `piRuntimeService.test.cjs`, `check-content-generation-agent.cjs`, `check-content-generation-output.cjs`, and `check-content-section-regeneration.cjs`.

`taskService.cjs` uniformly manages Technical Proposal (技术方案), Bid Duplication Check (标书查重), Disqualification Check (废标检查), and Blind Compliance Check (暗标合规检查) tasks; each business group is currently mutually exclusive within its group. The knowledge base is an explicit exception: `knowledgeBaseService.cjs` maintains the preparation/matching activity set per document and pushes it via `knowledge-base:event`. Word export has its own independent progress events.

Knowledge-base global search uses `knowledgeBase.search({ keyword, page })`, with pages starting at 1, returning `{ items, total, page, pageSize }` with 100 items per page. `total` and the current page are queried in the same SQLite read transaction; when data shrinkage makes the page number out of range, the last valid page is returned. Renderer displays using the returned page number and total, keeps the submitted keyword when turning pages, keeps the last successful page on failure, and lets an unfinished request expire when the search is cleared. Retrieval is still Main synchronous substring scanning; pagination does not imply full-text indexing or background-thread queries.

Managed tasks follow this flow:

1. Main creates a running task and persists the initial state.
2. High-frequency progress with no recovery value calls `updateTask()`, updating only Main memory and pushing events.
3. Stage results call `checkpointTask(taskPatch, workspacePatch, eventPatch)`, committing the task and business patch in one Store transaction, then pushing the same partial event after success.
4. Page unload does not cancel tasks; remounting restores the display from the Store and active-task replay.
5. The restart recovery policy after app restart is decided by `taskService.cjs` per task type: body-text tasks may become paused, outline waiting-for-selection only resumes when the persistent Session is intact, and other interrupted tasks usually become error. Renderer does not by itself turn a leftover running state into idle.

Main commands that clear tasks or downstream results must first cancel the relevant active tasks, wait for the runner to settle, then commit the Store; a cancelled runner must not checkpoint further. Technical Proposal (技术方案) and Disqualification Check (废标检查) import, delete, and reset already go through the `beforeCommit` chain of `taskService`; new entries should reuse that pattern.

### Blind Compliance Check (暗标合规检查)

"Bid Check (标书检查) → Blind Compliance Check (暗标合规检查)" (`features/blind-check/`) has four steps: select bid document, format requirements, check results, auto-fix. The architecture is program pre-screening + AI review: program checks are the `blind-check-inspect` action of OpenXmlHelper, handling only rules with explicit parameters, deterministic conclusions, and precisely modifiable behavior; anything requiring reading and understanding the tender (招标文件) or bid content is left to a persistent Agent (see "AI review" below). Protocol, rules, and evaluation semantics are documented in `openxmlhelper/开发说明.md`. On the Main side it consists of `blindCheckStore.cjs` (SQLite `blind_check_*` tables), `blindCheckPresets.cjs`, `blindCheckTask.cjs`, `blindCheckFixTask.cjs`, `blindCheckAgent.cjs`, `blindCheckReview.cjs`, and the thin IPC `blindCheckIpc.cjs`, with task types `blind-check-run` and `blind-check-fix`.

- Only `.docx` is accepted. On import, the file is copied to `workspace/blind-check/source/<UUID>.docx`; checks only run against the copy. Switching files or removing a file first cancels running checks and fixes and waits for the helper process to exit before committing; extracting presets from the tender document is independent of the document under check and is not cancelled by switching files — only reset cancels the whole group.
- Built-in presets are defined in `blindCheckPresets.cjs` and are read-only; regional presets are marked as reference values. Users must "Copy as my preset" before editing; user presets are saved in `blind_check_presets`. Preset fields only recognize what the engine actually uses; user input is normalized once in `normalizeProfile()`, unknown fields are dropped, and null means that item is not checked (the tender does not require it). Body text effects (`body.allow_*`), header/footer content, empty paragraphs, and paper size may all be null; the UI is a three-way choice of "tender does not require / disallow / allow". Table bold `table.allow_bold` with null means same as body text; table italic, color, and other effects always follow body text.
- The credential enterprise information from the qualification library (enterprise name and its suffix-stripped short name, credit code, legal representative, phone, email, address, account name, bank account) is read by Main when the check starts and passed to the engine as sensitive words; the switch is saved in `blind_check_meta.use_credential_words` and is not saved with presets. Person names are not included.
- The input signature consists of the document content hash, preset ID, normalized preset, and sensitive words (a preset ID represents the tender basis: the tender source text and provenance reviewed against are saved with the preset; two presets with identical format config but different IDs are still treated as different inputs), computed by Main (`getInputSignature`). Checks do not start automatically: on the "Check results" page click "Start check" ("Re-check" when results already exist), then choose in the dialog between program-only check or program check + AI review; the choice is passed with `tasks.startBlindCheck({ aiReview })`. When the signature differs from the existing result, the page shows that the result is expired. Progress is only pushed, not persisted; completion writes the merged results and task state in one checkpoint. On app restart, leftover running tasks are marked as failed.
- Color-image checking (preset `image.check_color`, off by default) needs pixel decoding: `blindCheckImageColor.cjs` uses adm-zip in Main to read PNG / JPEG (nativeImage can only decode these two), derives conclusions from the color-pixel ratio (only large images with a long side over 2048 px are downscaled; one- or two-pixel-wide colored borders in flowcharts become too small and are washed out by the white background), and passes it as `image_facts` to the engine; positioning, severity, and reporting remain the engine's job. When adding new preset fields, old user presets missing the field get defaults filled in `normalizeProfile()`; no migration is needed.
- "Generate from tender document" presets are completed by `blindCheckPresetExtractionTask.cjs` (task type `blind-check-preset-extraction`, mutually exclusive with checks and fixes within the group): the tender document takes the parsed body text of the Technical Proposal (技术方案) (`technicalPlanStore.readTenderMarkdown`) or a newly selected file converted by `fileService.parseBlindCheckTender` per the parsing config. `blindCheckPresetExtraction.cjs` first locates format clauses locally by format keywords (if nothing is found, it errors directly without calling AI) and only hands those fragments to AI; results are validated by type, range, and enum per field, Chinese numerals are converted by the program, each basis is matched back against the source after removing whitespace/punctuation, unmatched ones are kept but marked as unverified; items not mentioned in the tender (`CLEARED_WHEN_MISSING`) are set to not check, without inheriting the strict defaults of built-in presets: body, heading, table, margin, and other numeric formats get low-risk suggestions from consistency rules; text effects, header/footer content, empty paragraphs, paper size, and page numbers are directly not checked. Page number `structure.page_number` is tri-state: forbid means no page numbers allowed, footer_only means only page numbers may appear in the footer (all other footer content is reported; when the whole document has no page numbers it is a low-risk hint), null means unlimited. Switch-field extraction notes are bidirectional (both prohibitions and explicit allowances must be filled). A basis found in the source must also match the value direction (`valueIssue`: prohibition values need wording like "forbidden/prohibited", "footer may only contain page numbers" needs "only", numbers/sizes/fonts must appear in the basis); mismatches are marked as unverified with a reason. Clauses needing manual review are linked to related check items by keyword (`manualFields`); the extraction notes list these items' current settings so conflicts with effective check items are directly visible. After extraction, sentences in the format-clause fragments sent to AI are scanned by keyword (`findOmissions`); fields with no extraction at all and no manual-review clause become suspected omissions stored in `source_json.omissions`, with the original sentence shown under the corresponding field; fields must not be left empty — items not set to not-check during extraction (e.g. outline requirements) are listed in the extraction notes instead. Heading numbering format `structure.heading_numbering` (arabic for hierarchical Arabic numerals, null for not checking) may also be extracted. The result generates a new "my preset" and selects it; provenance (per-field values and bases, unrequired items, clauses that cannot be auto-checked, discarded items) is stored in `blind_check_presets.source_json` (v40), and the format-requirements page marks each item. Prompts and tasks live together, not in components.
- The format-requirements, check-results, and auto-fix steps share the `components/StepLayout.tsx` structure: title card (`StepHeader`, with preset selector and action buttons on the right) + tab bar (`StepTabs`, names + unit-bearing summaries, horizontally scrollable on overflow) + content card (`.blind-check-step-panel`, internally scrollable). Check-results tabs are All (summary as high/medium/low counts, with a risk card at the top of the content) and per problematic category (counts with high-risk counts, "Other" last); entering auto-fix uses the toolbar "Next step". Auto-fix tabs are fix items (enabled switch count) and fix results (fixed and pending-manual counts); after starting a fix it auto-switches to fix results. The UI does not distinguish whether a problem was found by the program or AI, or who fixed it; there is no separate AI tab. Problem cards (check results and fix results) use a uniform `components/IssueDetail.tsx` layout when expanded: gray labels on the left, content rows on the right (check results show tender requirement, problem description, fix method; fix results show reason not fixed, manual handling, handling status, modified content); "occurrence location" is also one row per occurrence, each with a location label + source excerpt; supplementary notes, format sources, and review reasons are appended as notes; titles of problems needing manual position confirmation carry a "needs manual confirmation" marker.
- The format-requirements page groups fields into five tabs by check object — page, body, headings and outline, tables and images, identity and traces (grouping is centralized in `features/blind-check/presetFields.ts` and is only a UI classification, not affecting preset field paths); editing traces, hidden information, document properties, and other identity-revealing checks share a tab with sensitive words. AI-generated presets have an extra trailing "AI extraction notes" tab; after extraction completes it auto-switches to that tab, and switching to a preset without provenance returns to the page tab. Bases of extracted values, failed verifications, suspected omissions, and "tender does not require" are all marked under each tab's fields (judgment semantics centralized in `fieldSourceNote()`); extraction notes only hold what does not fit under fields: source overview, suspected omissions that cannot be attributed under a field, clauses needing manual review, unrecognized results, and supplementary notes. A tab with warning hints under its fields (failed verification, or the source has related requirements but nothing is set) shows "N items pending review" at the front of its summary in the warning color (`presetTabPending()`), automatically disappearing after settings are corrected.
- After Technical Proposal (技术方案) "Export Word" completes, "Blind Compliance Check (暗标合规检查)" in the dialog imports the exported file into the blind check, sets the step to check results, and switches pages; the user clicks "Start check" on the results page. It does not auto-call AI to generate presets; when the current preset is a built-in one, the results page shows a hint.
- The fourth step "Auto-fix" calls the helper's `blind-check-fix` action via `blindCheckFixTask.cjs` (task type `blind-check-fix`, mutually exclusive with checks in the same group); the copy is written to `workspace/blind-check/fixed/<fileId>.docx`, leaving the original untouched. Only successful results with a signature matching the current check can be fixed; fix items are saved in `blind_check_meta.fix_rules_json`, fixable rules and default selections are in `FIX_RULE_IDS` in `blindCheckPresets.cjs`, and UI copy is in `features/blind-check/fixItems.ts`. English punctuation, redundant spaces, and columns are not tender format clauses (check results treat them as low-risk suggestions), and like paragraph page-break-before and grid alignment they are off by default; manual line breaks (split into paragraphs), heading numbering (renumber when the tender requires Arabic numerals, see the helper development guide), and outlines (delete when the preset forbids outlines; hand-made outlines without outline titles are left to humans) are on by default. Fix items are newly added; users who already saved selections need to check new ones themselves. Grayscale conversion of color images likewise needs pixel decoding, which the helper does not do: after checking, `writeGrayscaleCopy()` first converts images judged as color to grayscale, writes `fixed/<fileId>.gray.docx` as the helper's fix source, passes these images as non-color during recheck, and deletes the intermediate copy after fixing. Fix results are stored in v39 `blind_check_fix_results` / `blind_check_fix_groups`; switching/removing files and reset clear them together with the copies. Auto-fix is the last step; the toolbar replaces "Next step" with "Export fixed result" (same as the bid document's last step "Export Word"), and `checkResultExportService.saveBlindCheckFixedDocument()` pops a save dialog to copy the file out, defaulting to the original file's directory and forbidding overwriting the original; the workspace copy is not opened directly for users.
- AI review (v41): choose before each check in the dialog; the task stores the choice in `blind_check_meta.ai_review_enabled` (on by default, not counted in the input signature), only used as the next dialog's default. When AI review is selected, the check task runs the review phase after program results are persisted, within the same task (`runReviewPhase`); a review failure only records `blind_check_reviews` as failed, program results are still displayed, and re-check with AI review is needed (no separate re-run review entry; AI review only runs inside check tasks). Review creates a new persistent Session via `blindCheckAgent.cjs` (task key `blind-check-review`); the workspace is written with the full tender text (when AI extracts presets it is separately stored at `workspace/blind-check-tenders/<presetId>.md` and deleted with the preset; early and built-in presets have none, in which case clause bases can only come from preset provenance), format presets and provenance, program check results (group numbers `g{序号}`, positions with paragraph numbers, all entries of candidate groups), and the helper-exported bid structure. Sub-Sessions are subject to the Agent service's general sub-agent throttling and a 100-round cap per prompt (reset when a new prompt is sent; compaction does not reset), exceeding which aborts with `AGENT_TURN_LIMIT` without `max_retries` reruns; errors are handled by the caller. Main tasks have no round cap. Failure-diagnosis reporting is still only decided by `failure_handled_by_parent`. These rules are enabled by default at the service layer; business calls pass no parameters. State changes of each Runtime are merged in `agentService` to push at most every 250ms; Runtime pushes no longer query queues. AI queue concurrency caps cache for 1 second to avoid high-frequency synchronous config reads. Business tasks explicitly designate the main Session via `primary_session`; the execution monitor shows `active_tasks`; desktop-pet plugins only access the main Session. `services/agent/` and `services/pi/` only implement Runtime, Proxy, Session, tools, diagnostics, and persistent tasks, without referencing business Stores or business Prompts. Business adapters call through the `agentService` public interface.

Ordinary Agent workspaces are temp directories; outline generation V2 uses a persistent task workspace/Session to recover at the first-level-outline confirmation stage. Structured Agent output Schemas are defined in business task code and injected via `json_validation_schemas`; the Agent only passes `file_path` when calling `json-validation`.

Outline generation declares required products per stage: first-level outlines, sub-outlines, and count adjustments use `outline.json`. Score planning uses `technical-score-groups.json` and `score-directory-plan.json`; when user-approved new first-level outlines are added, new outlines are simultaneously inserted into `outline.json`. With multiple technical branches and word targets, the Agent fills `leaf-allocation.json`. Final review uses `outline.json` and `outline-review.json`. Template extraction uses `投标模版字段分类.json` (bid-template field classification JSON); final Word and field manifests are still generated by `openxml apply-template-fields`. Flows without scoring skip scoring and allocation files; single-branch or targetless allocation content is directly written by the program. Field-classification Schema is shared by template tasks and OpenXML tools; with zero candidates both classification arrays may be empty.

Runtime stage-handoff context provides `signal` and `onActivity`: when the program waits for subtasks or local export, pass the parent task cancellation signal and feed back real activity. Activities bind to the parent task identity, following the original idle-timeout rules. Handoff results may carry `await_before_prompt` (Promise), representing program steps parallel with context compaction: Runtime first registers its error handling, then executes compaction, waiting for it to complete after compaction before sending the next stage prompt. Its failure fails the task; task cancellation ends it by cancellation reason. Without it, behavior is unchanged.

The public Session factory first registers the task's base tools and all business tools, then enables current-stage tools before the first request. Pi SDK `tools` simultaneously restricts registration scope; stage-tool subsets cannot be directly used as registration lists. Later stages switch via `setActiveToolsByName()`, keeping the same Session and existing pre-execution gate. When the caller passes `fixed_tool_list: true` (Session factory `fixedToolList`), switch to enabling all tools at once; `setActiveTools` only updates the stage gate, with the gate rejecting currently unavailable tools before business execution callbacks and appending fixed notes to the system prompt. `snapshot.active_tools` means current-stage available tools; `registered_tools` is the actually enabled list. Default off; other task behaviors unchanged.

Runtime receives task or stage-handoff `prepare_output_files`, preparing blank files in UTF-8, create-only mode in the current workspace after writing stage inputs. Existing files stay as-is; repair rounds do not clear or reprepare. Prompts require the Agent to first fill empty files with `write`, supplementing with edit in multiple writes when content is large, accurately using workspace-root filenames. Outline and template tasks check all current-stage required products for non-empty, JSON, and structure requirements in `validateOutput`, only handing `validation_result` to out-of-loop `continueTask` for flow advancement after validation passes. Failed validation is returned to the original Session for repair per this section's "submission validation" fallback rules; execution failures still follow `max_retries`. Repair reuses existing content and user choices without repeating handoff side effects. Tasks provide file and operation details via `buildRetryPrompt(request, meta)`: `kind=execution` receives execution errors, `kind=submission` receives reports and repair modes. Execution exceptions are not disguised as submission problems; repair budgets and prompt rules are uniformly managed by the public layer.

`agentService.runTask()`'s `summary_enabled` defaults on; it is only off when explicitly passed `false`. The public Pi layer lets the Agent attach `task_complete=true` on the last batch of tool calls, ending the current stage directly after the whole batch succeeds. Main business tasks may also declare ending tools via the `is_final_tool_call` callback; the program then judges without providing completion markers to models. Tool failures continue processing; original result validation and multi-stage continuation run as usual. This parameter takes effect per call without writing global config; business calls decide whether to turn it off. Technical-proposal first-level and full outline generation, original-proposal restoration, bid-template extraction, and Global Facts (全局事实) generation have turned off closing summaries; Global Facts (全局事实) AI adjustment keeps summaries for UI display. Template extraction writes complete classification to `投标模版字段分类.json`; `openxml`'s `apply-template-fields` only receives `fields_file`. The tool automatically ends that task after tool completion file structure, candidate classification, Word validation, and product checks.

Agent questions are handled by the global `AgentQuestionDialogProvider` and Main Q&A/auto-confirm services; features do not implement a second waiting-Promise or dialog set.

Agents must not terminate tasks themselves: `report-failure` is uniformly changed by `pi/piTaskFailureTool.cjs` to a termination request; the tool first shows the reason to the user through the runtime question channel, reminding that continuing requires lowering quality, with fixed options "Continue with lower quality", "Terminate task", "Add handling requirements" (custom input). Only after user confirms termination does the task end with the existing `AGENT_REPORTED_FAILURE`, appending "(terminated per your choice)" (已按您的选择终止任务) to the error message, still counting in Agent failure statistics and diagnostics. When choosing continue or adding requirements, the tool returns relaxed instructions to the Agent: all quality requirements may be lowered or abandoned; the only bottom line is writing required files, passing program validation, and keeping the flow stably continuing, with user-added requirements taking priority. First confirmation in the same run allows auto-answer (auto-select continue); after choosing continue, requesting termination again turns auto-answer off (`auto_answer=false`), requiring manual choice. Termination-confirmation answers are not written to business-readable `user_question_answers`, only recording visible activity. Rules take effect at the tool layer for all Agents and all stages, regardless of whether the stage opens `ask-user`; "call report-failure" in business prompts needs no rewriting. Sub-Sessions with `failure_handled_by_parent=true` and Sessions without question channels (runtime environment self-check) keep directly reporting failures. Program-side termination after continuous submission-validation blocking is not in this rule.

Submission validation: file writes are not validated or intercepted at the write/edit layer; `json_validation_schemas` is only for Agent self-check. After the Agent ends a round, Runtime first restores protected files, then `validateOutput` returns a unified report `{ value, issues, progress?, minimumGoal? }`: each `issues` item uses `severity=blocking|quality` and `message` to describe problems, keeping other business positioning fields. Return an empty array when there are no problems. Errors affecting JSON reading, product integrity, HTML conversion, or necessary images are blocking; word counts, consistency, residual tables, and unfinished format补写/supplementary-writing are quality. Business validation normally returns reports; file reading, model interruption, and program exceptions still throw and follow `max_retries` without consuming submission-repair budgets. `pi/piSubmissionPolicy.cjs` uniformly maintains adjacent-two-round progress per stage: blocking-problem count first; when both are zero, compare quality-problem count or program-provided numeric remainder (word-count difference). One round without improvement requires changing methods; after two consecutive rounds without improvement, record-then-accept when only quality problems remain, or lower quality constraints with an explicit minimum goal and try one last round when blocking problems exist, terminating only when still blocked. The fixed three-attempt total cap is removed; continue repairing on improvement, without resetting on same-stage continuation, rebuilding policy only when truly switching stages or rerunning after pause. The public layer splices repair-mode notes; business callbacks only supplement file and tool information. On acceptance, `report.value` is passed as `validation_result` to out-of-loop `continueTask`, with放行/waived problems in `accepted_issues`. Final results keep `accepted_submission_issues` without disguising quality leftovers as repair success. Protected files are still managed by `pi/piWorkspaceBaseline.cjs`; registered inputs, non-target sections, original images, and ledgers are restored before submission with activity recorded, keeping image-block comparison. Body-text main stages reuse one manifest and section read, plus current-stage quality rules. Audit, table removal, and format补写/supplementary-writing completion tools only save submission requests; the main flow advances state only after acceptance. Shared edit subtasks check products once on exit and return problems and facts; repair decisions belong to main stages. Standalone single-section modification still has its own main-task submission policy. Submission problems spanning more than five sections continue using `fix-submission-issues`; others are directly modified by the main Agent. Outline, Global Facts (全局事实), body-text planning, original-proposal restoration, and template extraction all use the same report protocol, incompatible with old return structures. Checks reuse `node --test electron/services/pi/piRuntimeService.test.cjs` and `node scripts/check-content-generation-agent.cjs`.

- New document imports prefer reusing `fileService.cjs` / `parseDocumentWithConfig()`, keeping the config's local-or-MinerU choice, format fallback, image scope, and unified error copy. For missing-LibreOffice hints, reuse `DocumentParseNoticeProvider`.
- Word export uniformly goes through `exportService.cjs` and `window.savia.export.onWordExportProgress()`; Mermaid/HTML image conversion is completed locally by Main.
- Generated images are compressed by `electron/utils/imageCompression.cjs` before landing: AI-generated images in `aiService.cjs`'s `saveGeneratedImage()`, body-text HTML/Mermaid renders in `contentGenerationImageTools.cjs`'s `renderImage()`. Images exceeding 1920×2880 are proportionally downscaled, transparent areas flattened to white, uniformly converted to JPEG (quality 90). GIF or undecodable images are saved as-is. Subsequent body-text references, previews, Word export, and format self-check directly use compressed files; historical images are not migrated.
- Partial text modifications returned by AI reuse `electron/utils/textEdit.cjs`: use `applyTextEdit()` / `applyTextEdits()` with unique hits for unknown positions, `applyRangeEdit()` / `applyRangeEdits()` for known ranges. Unmatched or multi-matched cases should return errors; do not silently append replacement content to the end.
- Prompt prefix cache: model services only write cache at the end of the last message in a request; subsequent requests only hit when prefixes match verbatim at message boundaries. Identical prefixes within the same message, content-block splits, `cache_control`, and `prompt_cache_key` all have no effect. Materials shared across requests go as standalone messages before changing content; fixed rules are not placed after changing content. When issuing two or more concurrent or consecutive requests, first use `warmPromptPrefix()` in `electron/utils/promptPrefixCache.cjs` to send a prefix-only warm-up request (output cap 1; failures do not affect subsequent requests), constructing prefixes with the same function for warm-up and formal requests. Body-text batching (`sharedPrefixMessages()`), tender parsing (per tender segment), feasibility-study body text and proofreading, knowledge-base L1 block prefixes and multi-batch entries, and shared tender-source messages for disqualification/typo/logic checks are all organized this way.
- When troubleshooting anomalies, first record the reproducible stage, input summary, and error chain: developer-mode module logs use `createDeveloperLogger()` to write to `userData/logs/<module>/`; AI request logs are in `userData/logs/ai/`. Discardable file logs are asynchronously written via `silentFileLog.cjs`; log failures must not affect the main flow.

## Verification Checklist

| Change scope | Minimum verification |
|---|---|
| Renderer / TypeScript | `npm run build` |
| CSS / page layout | `npm run build`, then `npm run dev` to check target window size, internal scrolling, Dialog, and FloatingToolbar |
| Main / preload / IPC | Run `node --check <file>` for each changed `.cjs`, then run `npm run build` |
| IPC events, file selection, import, export, windows | After the above commands, use `npm run dev` to manually walk the full chain and confirm unsubscription and progress replay |
| Store / migration / background tasks | Above commands + `npm run smoke:electron-native`; manually verify saving, restart recovery, clearing, and interrupted states |
| Modules with corresponding `*.test.cjs` | `node --test <test-file>` |
| Dependency changes | `npm ci`, `npm run build`, `npm audit` |
| Windows / macOS packaging | `npm run dist:win` / `npm run dist:mac`; products in `release/` |
| Agent tools or packaged content | Run `scripts/verify-agent-tools.cjs`, `scripts/verify-packaged-agent-tools.cjs` accordingly |

When `npm run build` shows existing chunk-size warnings but exits 0, it still counts as success. When file paths are involved, cover at least Windows Chinese directories; when persistent tasks, IPC, or window lifecycles are involved, compilation alone does not count as verification complete.
