# Inicio de sesión del runner local

**Objetivo:** permitir al usuario activar o retirar expresamente la ejecución local al iniciar sesión en macOS y Linux, sin servicios alojados.

**Diseño:** los comandos `service-install` y `service-remove` gestionan exclusivamente un LaunchAgent de usuario en macOS o una unidad systemd de usuario en Linux. Usan la ruta absoluta de Node y del CLI instalado, junto con el archivo de configuración ya emparejado; nunca colocan el token en la definición. No sobrescriben archivos existentes y solo retiran un archivo propio reconocido. Se inician al instalar y al entrar en sesión; los errores terminales no producen reinicios automáticos en bucle. La conexión intermitente continúa usando los reintentos del runner. No se modifican servicios en el equipo de desarrollo ni se declara soporte Windows hasta contar con implementación y prueba.

1. Probar generación de definiciones con rutas especiales, errores, archivos ajenos y comandos de instalación y retirada simulados.
2. Implementar gestión local explícita, incluirla en distribución y describir cómo desactivarla; no ejecutarla durante desarrollo.
3. Verificar XML y sintaxis, pruebas focalizadas y runner empaquetado; declarar límites de plataforma.

**Avance:** `service-install` y `service-remove` están incluidos en el runner y documentados. Las pruebas simulan los gestores, protegen archivos ajenos, comprueban rutas especiales y conservan la definición si no se puede confirmar la reversión; el plist pasó `plutil -lint`. No se han instalado servicios reales ni probado las sesiones de usuario de macOS o Linux; Windows sigue pendiente. El runner coordina las instancias que usan la misma configuración mediante un bloqueo local. Conviene detener la instancia manual antes de instalar el servicio: si está activa, el proceso iniciado por el servicio no puede adquirir el bloqueo.

## Windows

Preparar una tarea de inicio de sesión para el usuario actual con `InteractiveToken`, rutas absolutas y sin incluir credenciales. Primero verificar la definición XML y el escape de argumentos con pruebas; luego integrar registro, arranque y retirada sin sobrescribir tareas ajenas, conservar la información necesaria si falla una reversión y probar los estados ambiguos. El soporte no se expondrá como terminado hasta validar instalación, arranque y retirada en Windows real. No registrar tareas durante el desarrollo en macOS ni habilitar ejecución alojada.

La función de definición ya genera XML de inicio de sesión con SID, privilegios limitados y rutas validadas; rechaza variables de entorno en las rutas y no incorpora el token de emparejamiento. Las pruebas verifican los caracteres XML y la sintaxis se comprobó con `xmllint`. La suite del runner pasó 490 pruebas y omitió 8 dependientes del entorno. La definición aún no se registra ni se ha validado contra el Programador de tareas de Windows; faltan el gestor, la recuperación ante fallos y las pruebas reales.

Al validar el XML contra el [esquema publicado por Microsoft](https://learn.microsoft.com/en-us/windows/win32/taskschd/task-scheduler-schema), la versión 1.4 inicial fue rechazada; se corrigió a 1.3 y la definición pasó la validación. `SAVIA_WINDOWS_TASK_SCHEMA=/ruta/al/esquema.xsd node --test runner/test/user-service.test.mjs` vuelve a ejecutar esa comprobación mediante `xmllint`. No sustituye el registro y la prueba en Windows. Antes de retirar una tarea, el gestor debe confirmar que la tarea registrada corresponde a la definición propia y a la identidad de la sesión; un archivo local con el marcador por sí solo no demuestra esa correspondencia.

Se preparó la lógica de coordinación con interfaces simuladas: comprueba identidad, privilegios, acción y disparador; conserva el registro mínimo sin credenciales cuando no se confirma la operación; y no sustituye ni retira una tarea ajena. La implementación efectiva del adaptador debe distinguir una tarea ausente de un fallo de consulta y crear sin sobrescribir tareas existentes. El adaptador, el almacenamiento persistente, la integración CLI y las pruebas en Windows real siguen pendientes; esta lógica aún no está expuesta al usuario.

El registro persistente está preparado: se crea sin sobrescribir archivos, valida su contenido y conserva únicamente rutas y SID. Una prueba con archivo real y Programador simulado comprueba la recuperación tras perder la respuesta al crear la tarea. La protección frente a enlaces simbólicos se probó en macOS; falta verificarla en Windows. Todavía no hay adaptador ni conexión al CLI, y no se ha registrado ninguna tarea real.

Existe un adaptador preliminar para el Programador mediante PowerShell y COM: comprueba el SID de sesión, registra con la opción de creación sin reemplazo, distingue la ausencia confirmada del error de consulta y verifica que no queden instancias después de detener. Las llamadas y fallos se probaron con ejecutor simulado y el analizador de PowerShell comprobó la sintaxis; no se ha ejecutado COM en Windows. Falta conectarlo al CLI y verificar el comportamiento real, la normalización de la definición consultada y las operaciones interrumpidas en Windows antes de ofrecerlo.

PowerShell real ejecutó la conversión del XML de prueba a la estructura usada por el gestor, con el objeto de tarea simulado; detectó acciones adicionales, cambios de contexto y disparadores desactivados. La comprobación ahora exige también un único principal y que la acción use ese principal. Se ejecuta con `SAVIA_TEST_PWSH=1 node --test runner/test/user-service.test.mjs` cuando `pwsh` está disponible. Esto no demuestra qué XML normaliza el Programador de Windows ni ejecuta COM.

La coordinación de servicio Windows ya reúne configuración emparejada, SID de sesión, registro persistente y adaptador; exige la misma identidad al retirar. Se probó con el archivo de estado real y un Programador simulado. Aún no se conecta al CLI: la obtención real del SID, la interoperabilidad con COM, el inicio, la retirada y la recuperación requieren pruebas en Windows antes de exponerla.

**Actualización:** los comandos del CLI ya están conectados en Windows. Una prueba aislada en Windows 10 con Node 22 registró una tarea con nombre temporal, ejecutó un programa ficticio y retiró la tarea; no se instaló el servicio de Savia del usuario. El Programador omite valores predeterminados y convierte el SID del disparador al nombre de la cuenta, por lo que la consulta normaliza esa identidad antes de compararla. Las pruebas reales también verificaron exclusión entre procesos, recuperación de un bloqueo tras terminar el proceso y rechazo de un bloqueo desconocido. Aún falta verificar el paquete independiente completo y la recuperación de operaciones interrumpidas en Windows.
