# Preparación del runner para Linux y contenedores

El runner empaquetado debe poder construirse y verificarse en Linux x64 y ARM64 antes de preparar una imagen para ejecución opcional. Preparar los binarios Pi fijados y el helper OpenXML de .NET para cada arquitectura, conservar la política de dependencias y la verificación de integridad, y no aprovisionar ni activar servicios alojados.

1. Añadir destinos Linux a la preparación de herramientas y helper con hashes oficiales y pruebas de empaquetado; no modificar los destinos existentes.
2. Verificar ejecutables y un flujo real del runner en un contenedor local para cada arquitectura disponible, incluyendo helper y tareas Pi simuladas.
3. Preparar imagen y persistencia del estado del runner con instrucciones de uso y límites; no desplegar ni activar Cloudflare Containers.

**Avance:** las herramientas rg, fd y jq se preparan para Linux x64 y ARM64 con hashes fijados de sus publicaciones; el helper se publica para ambas arquitecturas. Los seis binarios y el protocolo `ping` del helper se probaron en contenedores locales sin red; x64 se ejecutó mediante emulación. Debian mínimo carecía de ICU, necesario para la internacionalización del helper; la prueba usa la imagen oficial `runtime-deps` de .NET 10 con ICU. Se reproduce con `SAVIA_TEST_LINUX_DOCKER=1 node --test runner/test/linux-prerequisites.test.mjs` tras preparar las herramientas y helper para ambas arquitecturas y disponer de la imagen fijada por digest.

En esa primera etapa el empaquetador todavía rechazaba Linux, pendiente de validar la distribución completa y sus dependencias.

**Verificación adicional:** en contenedores Linux de ambas arquitecturas, Pi ejecutó una consulta con herramientas y proveedor simulado; el helper real generó un DOCX con texto Unicode e imagen PNG. Las pruebas no usaron red externa. El fixture de prueba combina Node 22 y las dependencias de .NET con ICU, fijados por digest; se ejecuta con `SAVIA_TEST_LINUX_DOCKER=1 node --test runner/test/linux-container-smoke.test.mjs` tras preparar los binarios. Estas pruebas montan los módulos de Node desde el árbol de desarrollo y no validan por sí solas una imagen de producción.

**Dependencias Linux verificadas:** se instalaron por separado en contenedores ARM64 y x64 con `node scripts/install-dependencies.mjs`, respetando el lockfile y sin scripts automáticos; cada instalación verificó 2.375 referencias. Usando los módulos propios de cada arquitectura, las pruebas de Pi simulado, `node:sqlite` y lectura de respaldos, y el Word real con imágenes PNG y WebP pasaron sin red. x64 se ejecutó bajo emulación. El runner usa `node:sqlite` para respaldos; no requiere el binario `better-sqlite3` de Electron para esa ruta. Las pruebas de contenedor aceptan `SAVIA_TEST_LINUX_DEPS_ARM64` y `SAVIA_TEST_LINUX_DEPS_X64` con rutas absolutas a instalaciones verificadas, además de `SAVIA_TEST_LINUX_DOCKER=1`.

**Distribución independiente:** el empaquetador admite Linux ARM64 y x64. Se construyó y probó una carpeta independiente por arquitectura, sin montar dependencias del checkout: pasaron el diagnóstico de integridad, Pi con proveedor simulado, SQLite, lectura de respaldos y exportación Word con PNG y WebP. x64 se ejecutó bajo emulación. En x64 también se comprobó `--prepare-cache` con metadatos inicialmente vacíos: verifica las fuentes y antigüedad del lockfile antes de preparar la caché, y el empaquetado final usa `--offline`, el lockfile fijado y scripts desactivados. La preparación y la distribución requieren espacio libre suficiente.

Tras retirar las copias temporales, la regresión de empaquetado en macOS ARM64 pasó con la versión final y sin descargas; `doctor` verificó el manifiesto, las herramientas y el helper. Sigue pendiente repetir la versión final en Linux ARM64, que había quedado sin verificar por agotamiento de espacio. No se ha probado un proveedor real ni x64 en hardware nativo. Todavía no existe una imagen de runner lista para producción y no se ha activado ni desplegado ejecución alojada.

**Regresión general:** `pnpm run test:runner` terminó con 401 pruebas aprobadas y ocho omitidas por requerir Docker, dependencias Linux o el helper real. En Miniflare pasaron en serie las cuatro pruebas centrales de autenticación y aislamiento, credenciales, concesiones de trabajos y emparejamiento. La suite completa de la API se interrumpió preventivamente por espacio libre insuficiente después de 38 resultados aprobados; estos resultados no demuestran que el resto de la suite pase.
